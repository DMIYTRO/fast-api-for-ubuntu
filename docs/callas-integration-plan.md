# План интеграции callas в Image Magic

Дата: 2 ноября 2026. Статус на 10 ноября 2026: этапы B, D, E, F реализованы и выключены флагами (см. [журнал](callas/CHANGES.md)); в production callas не включён. Продолжение — проверка и исправление процесс-планами, красочность, визуальные слои: [callas-preflight-plan.md](callas-preflight-plan.md).

Документ подготовлен по документации проекта и сверке перечисленных точек с рабочим кодом. Ссылки на старые аудиты служат навигацией: их перечни дефектов не считаются результатом нового воспроизведения. В рамках подготовки плана тесты обработки и нагрузочные тесты не запускались.

## 1. Зафиксированный объём

- Растр → PDF: существующий ImageMagick, политика DPI, масштабирования и подтверждения коррекций сохраняются.
- Объединение PDF: перевод на удалённый callas `merge`.
- Рендер PDF для превью: перевод на callas `render`, промежуточный PNG.
- Рамки, безопасные зоны и подтверждённые фальцы: существующий ImageMagick.
- Итоговые новые превью: JPEG, без WebP. Это изменение текущего рабочего PNG-контура, а не сохранение уже существующего JPEG-контура.
- PitStop, его профили, отчёты и блокировки отправки в печать сохраняются. Callas `process` в эту работу не входит.
- Новые результаты должны работать в карточках, истории, детальном просмотре, возврате через FTP/Sborka и существующих отчётах.

Ранее в `docs/pdf-audit/02-merge.md`, `03-preview.md`, `05-stability.md`, `06-callas-migration.md` был указан WebP. Для этой интеграции последнее решение пользователя о JPEG заменяет эти рекомендации. Исторические аудиты не переписываются как будто их выводы получены заново.

## 3. Где сейчас объединяются и рендерятся PDF

### 3.1. Обычная сборка

Источники: [аудит сборки](pdf-audit/02-merge.md), [batch_processor.py](../processing/batch_processor.py), [pdf_exporter.py](../core/pdf_exporter.py).

`BatchProcessor.create_pdfs` (`processing/batch_processor.py`, около строки 480) обрабатывает прошедшие проверку заказы. Для каждого заказа:

1. `_ordered_files_for_creation` определяет порядок сторон.
2. `_build_page_refs` строит соответствие логических страниц.
3. `_prepare_page_pdfs` сохраняет PDF-входы и конвертирует растры через `convert_image_to_pdf`; при необходимости предварительно выполняет коррекцию.
4. `merge_pdfs_with_pymupdf` (`core/pdf_exporter.py:79`) копирует страницы через `insert_pdf` и проверяет число страниц результата.
5. `_validate_created_pdf` проверяет созданный PDF, включая контрольный Ghostscript-рендер; результат атомарно заменяет `PDF/<stem>.pdf`.

В `core/pdf_exporter.py` есть и функция объединения Ghostscript; её наличие не означает, что она используется основным путём `create_pdfs`. Подмена должна происходить в подтверждённых вызывающих точках, а не только в одном вспомогательном модуле.

### 3.2. Отдельная сборка многослойных TIFF

Источник: [layered_tiff_print.py](../services/layered_tiff_print.py).

`build_reviewed_layered_print_pdf` (строка 74) собирает reviewed-PDF при отправке заказа в печать. Части извлекаются через PyMuPDF; финальное объединение также использует `insert_pdf` и `save` (примерно строки 236–254). Здесь нужны отдельное подключение callas и тесты. Локальное извлечение страниц и экспорт TIFF не заменяются автоматически вместе с объединением.

### 3.3. Превью

Источники: [аудит превью](pdf-audit/03-preview.md), [batch_adapter.py](../services/batch_adapter.py), [preview_generator.py](../core/preview_generator.py).

- `BatchProcessor.generate_pdf_previews` (`processing/batch_processor.py:730`) запускает Ghostscript `png16m` при 150 DPI, получает `page-*.png`, затем вызывает `generate_preview` для каждой страницы.
- `generate_previews_for_all` и `generate_previews_for_files` обслуживают превью готовых PDF и исходников соответственно. Растровые исходники могут идти сразу в ImageMagick.
- `BatchAdapter.process_order` (`services/batch_adapter.py`, примерно строки 188–326) выбирает источник превью. При включённом PitStop превью строятся из проверенного производственного PDF в `Previews/Final/<aggregate>/r0001/`; предусмотрены исходные превью при ошибках. Без PitStop существующая ветка использует исходники.
- `generate_preview` рисует разметку и сохраняет миниатюру до 480 px и детальную версию до 1800 px.
- `core/preview_cache.py` хранит детальную версию в `.preview-cache/<prefix>/<hash>.png`; ключ зависит от абсолютного пути миниатюры.

Заменяется рендер PDF для пользовательского превью. Ghostscript-контроль PDF при 72 DPI — другая операция; его сохраняем на первом этапе.

## 4. Параметры, которые необходимо сохранить или явно согласовать

| Поведение | Текущая реализация | Требование к интеграции |
| --- | --- | --- |
| Порядок сторон | `_ordered_files_for_creation`: face первым; единый двухстраничный PDF сохраняет порядок | Передавать `inputs` уже в этом порядке; callas ничего не пересортировывает |
| Имя PDF | stem лицевой стороны или единственного входа | Сохранить итоговое имя и путь приложения |
| Размер и DPI | `_prepare_page_pdfs`, `config/profiles.py`, политика resample | Оставить до callas; target DPI 300, текущую минимальную границу не менять |
| Ориентация | `rotation_degrees`, применяется при коррекции растра; страницы PDF сохраняются | Проверить 90/270°, не добавлять автоповорот при merge |
| Рендер | 150 DPI; текущая команда не задаёт CropBox/TrimBox | Сравнить область рендера callas с нынешней; проверить MediaBox/CropBox/TrimBox и поворот |
| Обычные рамки | зелёная `#28a745`, красная `#dc3545`; safe zone из профиля, обычно 4 мм | Сохранить геометрию и цвета |
| Толщина внешней рамки | параметр `bleed_mm=1` в превью; это не производственный вылет | Не подменять его значением вылета профиля, обычно 2 мм |
| Фальцы | `FoldOverlay`, зелёные зоны и пурпурные линии заменяют обычные рамки | Проверить half-fold, c-fold, z-fold и стороны |
| Цвет | текущая команда превью не задаёт ICC-преобразование | Проверить overprint, плашки, прозрачность; не обещать цветопробу без согласованного ICC-процесса |
| Формат | сейчас PNG в основном веб-контуре и кэше | Новый вывод JPEG; промежуточный PNG; чтение исторических PNG сохранить |
| Размеры превью | 480 и 1800 px | Сначала сохранить; качество JPEG подобрать по реальным файлам |
| Параллельность | `IMAGE_MAGIC_PREVIEW_WORKERS`, по умолчанию 2; плюс параллельность заказов | Ограничить число активных удалённых заданий и ожиданий; не занимать все потоки очередью |

При JPEG явно задать фон для прозрачных страниц, качество и параметры цветовой субдискретизации. Начальный кандидат — quality 95 и 4:4:4, окончательное значение принять после визуального сравнения; это предложение, не подтверждённая настройка проекта.

## 5. Повтор, отмена и перезапуск: текущее состояние

Источники: [аудит стабильности](pdf-audit/05-stability.md), [coordinator.py](../services/coordinator.py), [sql_repository.py](../services/sql_repository.py).

- `RunCoordinator` хранит контексты выполнения, очередь и ожидающие продолжения в памяти; заказы обрабатываются через `ThreadPoolExecutor`.
- Продолжение после подтверждения коррекции (`_pending_resumes`, около строки 525) работает внутри текущего процесса. Это не восстановление после перезапуска.
- `cancel` (строка 332) ставит флаг отмены; queued и waiting_confirmation завершаются сразу, для работающего запуска устанавливается `cancelling`. Из этого нельзя заключить, что уже запущенный внешний процесс прекращён.
- `SqlRunRepository.recover_interrupted_runs` (строка 497) при старте переводит незавершённые проверки в `failed`, stage `interrupted`, с причиной `application_restart`. Автоматического продолжения их обработки нет.
- Pending-действия печати/возврата сверяются со статусом и файлами, после чего становятся prepared либо failed. Автоматический откат перемещений после аварии намеренно отсутствует: нет постоянного манифеста перемещений.
- Новая обработка может заменить PDF по тому же итоговому пути; повтор HTTP-запроса callas и новый запуск проверки должны иметь разную семантику.

План: сохранять соответствие локальной операции и `job_id` до PUT. Повтор передачи одной операции использует прежний ID; новая проверка/изменённый вход — новый ID. После рестарта сначала сохраняем нынешнюю семантику interrupted: незавершённые локальные проверки не возобновляются автоматически. Отдельная сверка удалённых заданий отменяет оставшиеся или отмечает их завершёнными без публикации в устаревший запуск. Автовозобновление целого CheckRun потребовало бы отдельного изменения координатора и не должно скрываться внутри HTTP-клиента.

## 7. Этапы реализации и контрольные точки

### Этап A. Базовая выборка и контракт API

1. Сохранить схему OpenAPI без секретов; проверить точные поля merge/render, files, статусы, отмену и ограничения.
2. Выбрать тестовые заказы: face/back; единый двухстраничный PDF; разные размеры и повороты; кириллица; многослойный TIFF; overprint/плашки; повреждённый вход.
3. Получить результаты прежнего контура в отдельной тестовой папке, записать размеры страниц, порядок, время и внешний вид. Production-исходники не менять.
4. Выполнить одно явное сквозное синтетическое задание с машины приложения: доказать чтение входа сервером и чтение/проверку SHA результата приложением.

Готово, когда есть воспроизводимая база сравнения и подтверждённый контракт merge/render. Качество реальных клиентских файлов пока не подтверждено.

### Этап B. Настройки и клиент

Добавить настройки в `server/settings.py` и отдельный `services/callas/`. Предлагаемые параметры: `CALLAS_URL`, `CALLAS_TOKEN`, `CALLAS_SHARE`, раздельные флаги merge/render, таймауты, лимит одновременных заданий. По умолчанию оба новых обработчика выключены.

Клиент: PUT/GET/DELETE; ограниченный backoff; Retry-After; общий deadline с учётом каждого запроса и ожидания; отменяемый polling. Проверять пути результатов внутри папки конкретного задания, SHA и размер. Не логировать заголовки авторизации и полные ответы сервера.

Тесты с fake HTTP: done/failed/cancelled, 401/403/409/422, 429/503, потеря ответа PUT, плохой JSON, таймаут, отмена, ошибочный Retry-After и отсутствие секрета в логах. Тесты не обращаются к живым службам.

Готово, когда клиент и конфигурация проверены без изменения существующей обработки.

### Этап C. Учёт операций и файлов

Ввести постоянную запись операции: run/order/step, job_id, отпечаток параметров и SHA входов, состояние, пути, признак локальной публикации. При необходимости — Alembic-миграция с обратимым изменением схемы.

Загрузку входов завершать до PUT; не удалять входы, пока удалённый worker может их читать. Результат копировать во временный файл рядом с окончательным, проверять, затем replace. Не публиковать результаты отменённых и устаревших запусков. Учитывать очистку `.callas` через 24 часа и записей службы через 7 дней согласно предоставленной документации.

Тесты: повтор одной операции, разные параметры/изменённый вход по прежнему пути, авария до/после PUT, до/после публикации, неверный SHA, результат вне job-dir, отмена одновременно с done, недоступная/несмонтированная шара. Исходники остаются неизменными.

Готово, когда повтор передачи не дублирует работу и поздний результат не меняет завершённый запуск.

### Этап D. Обычная сборка merge

Подключить backend в `create_pdfs`, оставив подготовку растра, порядок и `_validate_created_pdf`. `skip_corrupt=false`: исключение страниц не допускается. Сохранить имя, итоговый путь, Troubles и последующую проверку PitStop.

Тесты: расширить `tests/test_pdf_creation_with_pdf_inputs.py`, `test_pdf_batch_validation.py`, `test_pdf_color_preservation.py`, `test_batch_adapter.py`. Проверять страницы и геометрию независимо от данных ответа службы. На реальных файлах отдельно сравнить OutputIntent, боксы и слои: сохранение этих свойств callas пока не доказано.

Готово, когда новый backend выдаёт полный PDF и проходит существующую проверку/PitStop в тестовом запуске.

### Этап E. Сборка reviewed layered PDF

Подключить merge в `build_reviewed_layered_print_pdf` после подготовки упорядоченных частей. Сохранить существующие проверки размеров, повторный PitStop и новую ревизию перед отправкой. Протестировать смешанный заказ, все стороны layered, отсутствие экспорта, несовпадение размеров и сбой сервиса. Сама публикация/отправка тестируется с fake Sborka.

Готово, когда оба пути финальной сборки покрыты и проверены отдельно.

### Этап F. Рендер и JPEG

Заменить только Ghostscript-рендер пользовательских PDF-превью на render PNG. Сохранить локальный прямой путь растровых исходников и диагностические превью при ошибке сборки. Проверять число страниц и сортировать по номеру страницы.

Обновить ImageMagick-вывод миниатюр и full на JPEG; добавить управление quality, фоном и субдискретизацией. Согласованно обновить кэш и поиск файлов, сохранив исторические PNG. Для новых превью хранить связь с SHA/ревизией PDF и устойчивый идентификатор кэша при перемещении.

Тесты: `test_preview_generator.py`, `test_preview_cache.py`, `test_return_preview_collage.py`, `test_ftp_preview_uploader.py`, `test_batch_adapter.py`; UI store-тесты и просмотр карточки/full/истории. Проверить RGB/CMYK, прозрачность, плашки, overprint, мелкий текст, рамки и фальцы. Линии сравнивать с допустимой погрешностью JPEG, а не побайтово. Если точная геометрия боксов callas отличается от старой, явно выбрать и зафиксировать политику до включения.

Готово, когда новые JPEG и старые PNG доступны во всех потребителях, качество принято на контрольных файлах.

### Этап G. Сбои, очередь и полный цикл

Проверить merge → локальная валидация → PitStop → render → рамки/JPEG → UI/отчёт → тестовая печать/возврат без реальных внешних отправок. Смоделировать обрыв API/SMB, занятые слоты, отмену, рестарт приложения и поздний ответ. Проверить ограничение параллельности и отсутствие зависших запусков/перезаписи результатов.

Регрессии: `tests/test_run_coordinator.py`, `tests/test_sql_run_repository.py` и тесты соответствующих workflow. Сначала целевые проверки, затем полный Python-набор и frontend tests/build. Измерить время заказа, p95 на выборке, размер превью, число сетевых запросов и объём временных файлов. Допустимые показатели установить по базовой выборке этапа A.

Готово, когда нет потери страниц/исходников, обхода PitStop, публикации устаревших результатов и поломки истории/возврата.

### Этап H. Внедрение и откат

1. Подготовить настройки и защищённый токен; проверить миграции, резервную копию БД и совместимость отката при изменении схемы.
2. Включить merge на контролируемой выборке новых запусков; затем отдельно render/JPEG.
3. Перезапускать именно `fastapi-app`; проверить новый MainPID, ExecMainStartTimestamp и active. Второй Uvicorn не запускать.
4. Проверять новые check runs; старые отчёты не доказывают применение изменений.
5. При проблеме выключить соответствующий backend и перезапустить службу. Учесть/отменить уже созданные удалённые задания. Сохранить принятые PDF и исторические превью.

Не вводить неявный автоматический fallback на прежний backend при любом сбое. Оператор получает понятную русскую ошибку; ручное переключение управляемо и проверяемо. Полный запуск после рестарта остаётся новым запуском, пока не реализована отдельная функция восстановления.

## 8. Команды финальной проверки

```bash
.venv/bin/python -m pytest -q
cd frontend
npm test -- --run
npm run build
```

Целевые наборы выбираются по изменённым модулям перед полным прогоном. Для интеграционных проверок нужны `magick` и `gs`; обычные тесты API используют fake. Живые smoke-тесты запускаются явно на тестовых файлах, не внутри общего pytest.

## 9. Что ещё нужно перед приёмкой

- Реальные PDF с overprint, плашками, прозрачностью и ожидаемым визуальным результатом.
- Принятое качество JPEG на миниатюре и полном просмотре.
- Проверка особенностей merge/render по OpenAPI и сквозному заданию: одного health недостаточно.
- Утверждение допустимого времени обработки по фактической базовой выборке.

Остальные решения зафиксированы выше; профили callas для process, замена PitStop и перенос растровой конвертации на сервер в эту реализацию не требуются.
