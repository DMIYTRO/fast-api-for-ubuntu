# Журнал действий заказа

`GET /api/checks/{run_id}/orders/{aggregate_id}/actions` (требует авторизации)
возвращает `{schema_version: 1, items: [...]}`. Тот же журнал доступен в карточке
в разделе «Действия с заказом» и обновляется при открытии.

Запись: `id`, `kind`, `label`, `created_at`, `status`, `pdf_revision`,
`pdf_sha256`, `details`. Идентификатор события стабилен в пределах запуска.
Данные берутся из постоянного журнала событий (включая его архив), отдельная
таблица и миграция не нужны. Для старых событий без `aggregate_id` совпадение
по номеру заказа разрешено только при единственном клиенте с таким номером.

Отражаются завершение проверки, подтверждение/отказ коррекции, фактические
коррекции размеров и повороты, успешное сведение TIFF, создание PDF, проверки
PitStop, запуск/завершение и решение по исправлению Callas, перемещения в
печать/доработку и их отмена. Сведения о TIFF и автоматических коррекциях
находятся в `details` события проверки. Принятие кандидата Callas означает
решение оператора; результат повторной проверки хранится отдельным событием
ревизии. Абсолютные пути, полный отчёт и сетевые ответы в ленту не копируются.

Изменения шрифтов/профилей пока не выводятся: текущие инструменты не дают
подтверждённого структурированного события об этих изменениях. Новые типы
действий можно добавить в проекцию `services/order_actions.py`, когда появится
соответствующий источник фактических данных. История до внедрения записи
событий Callas не восстанавливается из текущего `state.json` задним числом.
