# Callas как уровень проверки и исправления: план

Дата: 10 ноября 2026. Статус: план; в приложении реализованы только `merge` и `render`
(см. [callas-integration-plan.md](callas-integration-plan.md) и [журнал](callas/CHANGES.md)).

Этот документ продолжает план интеграции: добавляет процесс-планы pdfToolbox (проверка и
исправление), проверку красочности, визуальные слои на карточке заказа, PitStop для заказов
с ошибками локальной проверки и единый список ошибок.

### Живая проверка

Копия реального заказа (визитка 90×50, 4-4, 2 страницы), запросы с машины приложения,
вход скопирован в `/mnt/shared/.callas/<job_id>/in`:

| Задание | Время | Результат |
| --- | --- | --- |
| `inkcoverage`, 72 ppi, `TrimBox` | 1,0 с | по каждой странице список красок с процентом покрытия; плашек нет |
| `visualizer`, 150 ppi, JPEG, виды `full`, `sep_process`, `sep_spot`, `ink_temp`, `safety_zone` | 1,5 с | 14 файлов, 589 КБ; в ответе `layers` (страница → вид → файл) |
| `process`, `analyze`, `PDF analysis/List potential printing problems` | 1,0 с | `result_status: warnings`, счётчики в `summary`, XML-отчёт 97 КБ |

Не проверено: нагрузка пачкой заказов при 8 слотах, большие форматы, PDF с плашками,
прозрачностью и DeviceN, режим `fix`.

### Что отдаёт `process`

- Ответ задания: `exit_code`, `result_status`, `summary` (`errors`, `warnings`, `infos`,
  `fixups_applied`, `fixups_failed`), список файлов.
- Подробности — только в XML-отчёте (`<имя>_report.xml` в `out_dir`): `<hits rule_id severity>`
  и `<hit page llx lly urx ury>` с координатами объекта.
- `rule_id` вида `RUL71` — порядковый номер внутри одного отчёта. Устойчивый ключ для
  сопоставления — название правила (`display_name`) из блока `profile_info`.

### Ограничения, которые влияют на приложение

- `inkcoverage` даёт среднее покрытие по рамке, а не максимум суммы красок (TAC). Превышение
  TAC ищется видом `ink_temp` визуализатора с порогом `inkcov` и `only_problems: true`:
  пустой набор означает, что превышения нет.
- 10 ppi в `inkcoverage` — грубая оценка; для решений использовать 72 ppi.
- `visualizer`, `inkcoverage`, `process` и `render` делят одну полосу очереди. Общий таймаут
  новых типов — `CALLAS_VISUALIZER_TIMEOUT` (600 с).
- `DELETE /jobs/{id}` не удаляет папку задания на шаре; её чистит приложение.

## 2. Как запрос превращается в обработку заказа

1. UI отправляет `POST /api/checks` (`control_panel.py`, `start_check`) с папкой, направлением и опциями.
2. `RunCoordinator.submit` ставит запуск в очередь; рабочий поток сканирует папку и группирует
   файлы `face`/`back` в заказы.
3. `BatchProcessorAdapter.process_order` (`services/batch_adapter.py`) для каждого заказа:
   локальные проверки → PDF → PitStop → превью той же ревизии PDF.
4. Callas: входы копируются в `/mnt/shared/.callas/<job_id>/in`, затем `PUT /jobs/{job_id}`,
   опрос `GET /jobs/{job_id}`, результат из `out` со сверкой SHA-256.
5. PitStop — отдельно, через SSH и SMB. Прогресс уходит в UI по SSE.

## 3. Этапы в приложении

### Этап 1. Callas как уровень проверки (`analyze`)

- `CallasClient.process()` и разбор XML-отчёта в `services/callas/` по образцу `services/pitstop/parser.py`.
- Каталог процесс-планов в `config/`: план, направление (`digital`/`offset`), режим, переменные,
  блокирует ли печать.
- Порядок: сборка PDF → Callas analyze → PitStop → превью.
- Результат — отдельный блок `callas` в заказе рядом с `pitstop`: миграция Alembic, поле DTO,
  флаг `IMAGE_MAGIC_CALLAS_PROCESS_ENABLED` (по умолчанию выключен).

### Этап 2. PitStop для заказов, не прошедших локальную проверку

- Сейчас `process_order` при `not order.passed` сразу выходит, а `create_pdfs` такие заказы
  пропускает, поэтому PitStop их не видит.
- Для таких заказов собирать диагностический PDF «как есть», без коррекций, в отдельную папку
  (например `PDF/Diagnostic/`) и отправлять его в PitStop и Callas.
- Статус заказа остаётся `error`; диагностический PDF не становится производственным и в печать не уходит.
- Если PDF собрать нельзя (битый файл) — `not_checked` с причиной.

### Этап 3. Единый список ошибок

- Источников три: `order.errors`, `processing_errors`, отчёт PitStop; добавится Callas. Сейчас
  группировка только на фронте по точному тексту (`issueGroups.js`, `PitStopReport.vue`).
- Единая запись на бэкенде: `code`, `severity`, `source` (`local`/`pitstop`/`callas`), `message`,
  `page`, `file`, `count`.
- Таблица соответствий: `action_id` PitStop и название правила Callas → канонический код с русским
  текстом; там же списки скрытых и объединяемых кодов.
- На карточке — один список по кодам с метками источника; полные отчёты доступны по ссылке.

### Этап 4. Красочность и визуальные слои на карточке

- Красочность: заявленная из имени файла (`4-4`, `4-0`) против фактической из `inkcoverage`
  (72 ppi) по каждой странице, включая плашки. Несовпадение — предупреждение.
- Слои в `PreviewViewer`: «Макет», «Сепарации», «Покрытие краской», «Безопасная зона» — одно
  задание `visualizer`, вкладки строятся по `layers` из ответа.
- Хранение: `Previews/Final/<aggregate>/r0001/callas/`.
- Цифры считаются при проверке; изображения слоёв строятся по запросу и кэшируются.
- Дополнительно: подсветка объекта на превью по координатам из отчётов PitStop и Callas.

### Этап 5. Процесс-планы с исправлением (`fix`)

- Исправление создаёт новую ревизию PDF (`r0002`), исходная сохраняется; PitStop и превью
  выполняются заново для новой ревизии (`current_pdf_revision`).
- Планы двух классов: безопасные (автоматически) и требующие подтверждения — через
  существующую паузу `waiting_confirmation` с показом «до/после».
- Инвариант «не конвертировать цвет автоматически» сохраняется: план, меняющий цвет, идёт
  только через подтверждение.

## 4. Открытые вопросы

- Собственный процесс-план (`.kfpx`) и набор макетов, которые он должен ловить, плюс контрольные «чистые».
- Должны ли ошибки Callas блокировать отправку в печать, как PitStop. Предложение: начать с предупреждений.
- Callas в production выключен: в окружении `fastapi-app` нет `IMAGE_MAGIC_CALLAS_URL` и токена.
  Включение — `sudo scripts/enable_callas.sh`, перезапускает службу.
