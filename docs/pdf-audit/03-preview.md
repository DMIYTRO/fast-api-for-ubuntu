# Этап 3. Превью из PDF и из исходников

Статус утверждений: **[код]** проверено чтением текущих файлов; **[опыт]** воспроизведено локально в scratch на синтетических файлах (ImageMagick 7.1.2-29, Ghostscript 10.06.0); **[предположение]** не проверено. Production, общая шара и реальные заказы не использовались. callas не запускался.

## 1. Сверка с описанием заказчика: «PDF в TIFF»

**Не совпадает. TIFF как результат превью в коде не создаётся нигде.** [код]

| Шаг | Вход | Выход | Инструмент | Где |
|---|---|---|---|---|
| Промежуточный рендер | PDF | PNG 8 бит на канал RGB, 150 DPI | Ghostscript `png16m` | `processing/batch_processor.py:756-766` |
| Превью для карточки и истории | PNG из шага выше или исходник TIFF/JPEG/PNG | PNG до 480 px | ImageMagick | `core/preview_generator.py:207-208` |
| Детальное превью | то же | PNG до 1800 px в кэше | ImageMagick | `core/preview_generator.py:217-226`, `core/preview_cache.py:66` |
| Композит слоёного TIFF | TIFF → PDF | PNG до 1800 px | ImageMagick + PyMuPDF | `control_panel.py:309-320`, `services/layered_tiff_print.py:36-48` |
| Лист возврата в Sborka | PNG-превью | PNG, высота 1000 px | ImageMagick | `services/return_preview.py:98-120` |

Где встречаются другие форматы:

- **TIFF** только как вход (исходник заказа).
- **JPEG** в рабочем контуре только как вход и как ручная загрузка оператора до 1 МБ (`control_panel.py:1075-1078`).
- JPEG-вывод есть в `generate_preview.py:55` и `batch_inspector.py:121`. Это автономные скрипты: импортов из рабочего контура не найдено.
- `plain_pdf_preview.py` делает обратное: растр → PDF. Он тоже нигде не вызывается.
- `.preview-cache` в корне репозитория содержит 39 PNG, многие по 12-22 байта, в плоской раскладке от 23 сентября. Текущий код пишет в подпапки `xx/`. Похоже на следы тестов [предположение]. Рабочий кэш лежит на шаре и не осматривался.

**Что уточнить у заказчика:** нужен ли действительно TIFF (например, как контрольный растр для другого процесса) или имелась в виду растеризация PDF. Для экрана и Sborka нужен PNG/JPEG. TIFF стал бы новым требованием, а не заменой существующего.

## 2. Как работает

1. Запуск: `process_order` создаёт превью по ветке результата (`services/batch_adapter.py:188-326`). Галочка UI `generate_previews` (`frontend/src/components/StartCheckPanel.vue:44`) отключает всё.
2. Выбор источника [код]:
   - заказ не прошёл, PDF не включён или сборка PDF упала: превью из исходников (`:223-224`, `:234-235`, `:244-251`);
   - PDF собран, PitStop включён: превью из итогового PDF в `Previews/Final/<aggregate_id>/r0001/` (`:275-295`), запасной вариант из исходников (`:300-306`);
   - **PDF собран, PitStop выключен: превью из исходников, а не из PDF** (`:307-310`).
3. Рендер PDF: команда ниже, затем каждая страница уходит в `generate_preview` (`batch_processor.py:783-806`).

   ```
   gs -q -dSAFER -dBATCH -dNOPAUSE -sDEVICE=png16m -r150 -sOutputFile=<tmp>/page-%03d.png <pdf>
   ```

4. Рендер исходника: файл сразу подаётся в `magick`, DPI из метаданных или 300 (`batch_processor.py:886-898`).
5. Разметка, один из двух режимов (`core/preview_generator.py:177-205`):
   - обычный: зелёная `#28a745` рамка толщиной 1 мм по краю изображения, красная `#dc3545` на отступе `safe_zone_mm` (4 мм, `config/profiles.py:20`);
   - подтверждённый фальц: вместо рамок линии `#ff00ff` и зелёные зоны по панелям.
6. Два прохода `magick` с одним набором рисования: `-resize 480x480>` и `-resize 1800x1800>` (`:207`, `:220-226`).
7. Выдача: `GET /api/files/{id}/preview?size=thumbnail|full&page=N` (`control_panel.py:975-1023`), заголовок `private, no-cache, must-revalidate`. При отсутствии детальной версии 404, при ошибке настройки кэша 503.
8. Переходы заказа перемещают файлы превью в `Previews/Processed/` или `Troubles/<order>/` (`services/file_lifecycle.py:70-74`, `:89-97`).
9. Возврат: выбирается пользовательское превью, одно готовое или лист из нескольких; загрузка по FTP в `inbox/press/`, затем запрос в Sborka (`services/return_preview.py:137-231`, `services/order_workflow.py:659-675`).

### Параметры

- **DPI:** 150, задан по умолчанию и нигде не настраивается (`batch_processor.py:734`). Контрольный рендер проверки PDF отдельный, 72 DPI (`:630-631`), его результат превью не использует.
- **Цветопроба: нет.** Нет ICC-профилей, `-sOutputICCProfile`, `-profile`, `-colorspace`, симуляции бумаги. [код] Команда `magick` из CMYK-TIFF без профиля дала для `cmyk(100%,0,0,0)` чистый `srgb(0,255,255)` [опыт], то есть неуправляемое преобразование.
- **Боксы PDF: игнорируются.** На PDF с MediaBox 400, CropBox 300, TrimBox 200 pt рендер дал 400×400 px при 72 DPI, то есть весь MediaBox [опыт].
- **Параллельность:** `IMAGE_MAGIC_PREVIEW_WORKERS`, по умолчанию 2, ограничено числом ядер и файлов (`batch_processor.py:71-78`). Она умножается на число одновременно обрабатываемых заказов. Итоговый PDF всегда один элемент, поэтому один поток; его страницы идут последовательно (`:783`, `:833-839`). Параллелятся только исходники.
- **Таймаут:** 300 с на каждый вызов инструмента, `IMAGE_MAGIC_TOOL_TIMEOUT_SECONDS` (`core/tool_runner.py:11`, `:17-27`).
- **Кэш:** `<IMAGE_MAGIC_INPUT_DIR>/.preview-cache/<xx>/<sha256>.png`, ключ это sha256 абсолютного пути файла-миниатюры (`core/preview_cache.py:63-66`). Содержимое PDF, ревизия и размер в ключ не входят.
- **Инвалидация кэша: нет.** Обновление возможно только перезаписью по тому же пути; очистки в коде не найдено, включая `.work`.
- **Связь с ревизией:** только имя папки `r0001`, зашитое константой (`batch_adapter.py:280`). SHA256 PDF хранится у заказа, но у превью нет ни хэша, ни номера ревизии.

## 3. Проблемы

Серьёзность: **В** может дать неверное решение по печати или блокировку заказа; **С** заметный сбой или лишняя ручная работа; **Н** незначительно.

### В1. Без PitStop оператор смотрит не на печатаемый PDF [код]

Сценарий: PitStop выключен (по умолчанию выключен, `CLAUDE.md:42`). Сборка PDF ошиблась с разворотом, порядком или обрезкой, но прошла проверку. Оператор видит корректные исходники и отправляет в печать. Комментарий в `batch_adapter.py:308` объясняет это отсутствием ревизии, но PDF в этот момент уже есть. Кроме того, `README.md:394` утверждает, что превью исходников сохраняются до PitStop, а код создаёт их только как запасной вариант.

### В2. Многокадровый TIFF: файл превью не появляется, а путь считается созданным [опыт + код]

`magick m.tif ... o.png` на двухкадровом TIFF создал `o-0.png` и `o-1.png`, файла `o.png` нет, код выхода 0. `generate_preview` не указывает `[0]` и `tiff:ignore-layers=true` (`core/preview_generator.py:177`), хотя сборка PDF это делает, и не проверяет результат. Путь попадает в `preview_paths` (`batch_processor.py:899`).

Следствия: нет картинки; `accept_for_print` падает с «Не найдено или повреждено превью» (`file_lifecycle.py:70`, `:145-148`). `core/inspector.py:33-35` указывает, что Photoshop-слои видны как кадры, поэтому слоёный TIFF с одним слоем, который разрешён с предупреждением (`batch_processor.py:141-145`), подвержен тому же [предположение: на реальном Photoshop-TIFF не проверялось]. Обход «если обычное превью пропало» в `return_preview.py:171-176` выглядит как следствие этой причины [предположение].

### В3. Рамки не показывают реальную линию реза [код + опыт]

Рамки считаются от края растра, а рендер идёт по MediaBox.

- PDF с полями или метками: рамка на краю MediaBox, безопасная зона от него же. TrimBox не участвует.
- Файл с вылетом (`bleed_mm` 2, `config/profiles.py:21`, `:41-43`): рамка «реза» на внешнем крае вылета, настоящая линия реза не нарисована, а 4 мм фактически дают 2 мм от реза [предположение: для направлений, где размер файла включает вылет; уточнить с этапом generation].
- `generate_preview.py:6-7` описывает обратные цвета (красный край, зелёная зона). Оператору легко перепутать, если инструкции писались по этому скрипту.

### В4. Цвет превью не соответствует печати [код + опыт]

CMYK, плашки, наложения и ICC не моделируются (см. параметры). Для проверки компоновки это допустимо, для цветового решения нет. В UI предупреждения о некалиброванном цвете не найдено [предположение: искал только в связанных с превью компонентах].

### В5. Новая ревизия PDF не получает нового превью [код]

Печать из просмотренных TIFF создаёт новый PDF и повышает `current_pdf_revision` (`order_workflow.py:514-515`, `:562`), но генерации превью в этом потоке нет: она вызывается только из `batch_adapter`. Заказ получает ревизию 2 с превью `r0001`. Проверки ревизии охраняют PDF, а не картинку. Повторный запуск того же заказа пишет в тот же `r0001`, поэтому номер не уникален между запусками.

### С1. Кэш теряется при перемещении файлов [код]

Ключ зависит от пути миниатюры. После перехода в `Previews/Processed` или `Troubles` путь иной, детальный файл тот же не находится: «Детальное превью ещё не создано» (`control_panel.py:1010-1015`), хотя файл лежит в кэше. Это затрагивает и отправленные на доработку заказы, которые оператор открывает повторно.

### С2. Защита от незамонтированной шары не работает [опыт + код]

`_is_external_mount` идёт вверх до `/`, а `/` всегда точка монтирования, поэтому функция вернула `True` для обычного каталога на корневом ext4 (`core/preview_cache.py:14-21`). Сценарий: шара отвалилась, запись уходит на системный диск вопреки комментарию `:39-40`. Все тесты подменяют эту функцию, поэтому дефект не виден (`tests/test_preview_cache.py:14`, `:54`).

### С3. Лист возврата растянут из миниатюры [код]

На вход идут версии 480 px, команда `-resize x1000` увеличивает их примерно вдвое (`return_preview.py:107-108`). В Sborka уходит размытая картинка, хотя версия 1800 px есть в кэше.

### С4. Пользовательское превью игнорируется при совпадении номера заказа [код]

При конфликте номеров у разных клиентов файл сохраняется под `aggregate_id` (`control_panel.py:338-349`), а возврат ищет его по голому `order_id` (`order_workflow.py:298`, `:450`; `return_preview.py:145`). Оператор загрузил своё превью, а уходит сгенерированное. Имя листа `{order_id}_return-preview.png` тоже общее для таких заказов (`return_preview.py:98`) и может быть перезаписано.

### С5. Отключение превью блокирует печать [код]

При снятой галочке `preview_paths` пуст, а `_required_paths` требует хотя бы один путь (`file_lifecycle.py:145-148`). Заказ можно проверить, но нельзя принять.

### С6. Запись не атомарна [код]

`magick` пишет сразу в целевой файл (`preview_generator.py:208`, `:224`). Возможны частичная картинка при чтении UI; новая миниатюра рядом со старой детальной версией, если второй проход упал; страницы-сироты при сбое на середине PDF. На слоёном TIFF уже применён правильный приём: временный файл и `os.replace` (`control_panel.py:305`, `:321-322`).

### С7. Позиционная привязка превью к файлу в БД [код]

`preview_paths[index]` сопоставляется с `order.files` по индексу (`sql_repository.py:715`). Производственные превью идут face-first (`batch_adapter.py:333-337`), а файлы приходят в порядке сканирования по имени (`batch_processor.py:83`). Если `back` сортируется раньше `face`, в БД стороны меняются местами; это читает история (`control_panel.py:1329-1330`). Для двухстраничного PDF вторая страница в колонку `preview_path` не попадает. DTO, напротив, связывает по имени (`dto.py:76-85`), так что источники расходятся.

### С8. Противоречие при возврате без превью [код]

`prepare_return_preview_name` намеренно возвращает `""` для старых случаев (`return_preview.py:218-222`), но при настроенном FTP `_return_preview_upload_paths` на пустом имени бросает ошибку (`order_workflow.py:149`). Возврат откатывается, хотя `README.md:345` обещает отправку без превью.

### С9. Накладные расходы и рост хранилища [код]

- Рабочие файлы и PNG на 150 DPI пишутся на шару, каждый исходник декодируется целиком дважды, плюс `inspect_file`.
- Кэш и `.work` не чистятся: сбой процесса оставляет каталоги, а кэш растёт без предела.
- Для больших форматов лимит 300 с действует на каждый вызов; превышение станет ошибкой превью, а не заказа.

### Незначительные

- **Н1.** Фальц всегда вертикальный: `axis` не передаётся (`batch_adapter.py:148`), поэтому горизонтальный фальц рисуется неверно. Для фальца `span_mm` берётся из заказа, а пиксели включают возможный вылет.
- **Н2.** При подтверждённом фальце рамки реза пропадают совсем (`preview_generator.py:179`), это задумано, но оператор их не видит.
- **Н3.** Нет `-auto-orient` в `generate_preview`, хотя в листе возврата он есть: JPEG с EXIF-поворотом проверяется и показывается по-разному [предположение о видимом эффекте].
- **Н4.** Подстрока `side in stem` (`control_panel.py:1004`) и префикс `stem_` (`dto.py:79`) могут дать ложное совпадение на именах вроде `Feedback` или `abc` / `abc_2`.
- **Н5.** FTP: `STOR` прямо в целевое имя, без повторов (`ftp_preview_uploader.py:60-61`).
- **Н6.** `_remove_uploaded_previews` нигде не вызывается (`order_workflow.py:152`). Включать её нельзя: история читает `Previews/Return` (`control_panel.py:371-374`). Лучше удалить.
- **Н7.** Сканирование `Previews/Processed` по маркеру `-{id})` (`return_preview.py:178-186`) может подмешать файлы прошлого прогона в той же папке.
- **Н8.** Без `IMAGE_MAGIC_INPUT_DIR` корень кэша вычисляется как `parent.parent` от пути миниатюры (`preview_cache.py:36`), то есть зависит от глубины папки. Касается разработки и CLI.

## 4. Улучшения стабильности

Сделать независимо от callas, по приоритету:

1. Для PDF всегда рендерить превью из итогового файла, вне зависимости от PitStop (В1).
2. Читать только композит: `-define tiff:ignore-layers=true` и `[0]`; после `magick` проверять существование и ненулевой размер (В2).
3. Писать во временный файл рядом с целью, затем `os.replace` (С6).
4. Ключ кэша: `sha256(содержимое PDF или исходника) + страница + версия рендера`, путь исключить. Закрывает С1 и часть В5. Добавить очистку по возрасту и уборку `.work`.
5. Записывать при каждом превью метаданные: SHA256 источника, ревизия, страница, сторона; UI предупреждает при расхождении с `current_pdf_sha256`. Заменить индекс в БД на привязку по файлу и странице (С7).
6. Повторно рендерить превью после новой ревизии (В5).
7. Проверять монтирование конкретного корня: `os.path.ismount(input_root)` или сравнение `st_dev` с родителем (С2).
8. Лист возврата собирать из версии 1800 px (С3); `custom_return_preview_path` вызывать с тем же идентификатором хранения (С4).
9. Единообразно определить условия обязательности превью (С5, С8).
10. Показывать в UI подпись «Цвет ориентировочный» и легенду рамок.

## 5. Что заменяется в callas

**Ответ на вопрос этапа callas:** да, можно заменить только растеризацию и оставить рамки ImageMagick [код]. `generate_preview` принимает любой растр, размеры и DPI. Менять нужно блок `batch_processor.py:751-780`.

Зависимости этого блока:

- обнаружение `page-*.png` и сортировка по имени в `:778`;
- порядок страниц, который задаёт сопоставление с `page_names` (`:785-791`);
- `inspect_file` должен прочитать ширину, высоту и DPI: DPI рендера нужен для перевода миллиметров в пиксели (`meta.dpi or render_dpi`, `:798`). Если callas не запишет разрешение, сработает запасной `render_dpi`, поэтому передавать надо фактическое значение;
- остальной код зависит не от `page-%03d.png`, а от итоговых `*_preview.png`: `return_preview.py:166`, `:183-186`, `:205`, `report_builder.py:312`, `dto.py:79`.

| Сейчас | В callas | Статус |
|---|---|---|
| `gs png16m -r150` для превью PDF | `--saveasimg` (`callas-pdftoolbox-test-guide/COMMANDS.md:95`) | Заменяется. Параметры DPI, боксов, формата и профиля надо подтвердить по `pdfToolbox --help saveasimg`: в гиде их нет |
| `gs -r72` контроль страниц | возможно тот же вызов | Решает этап verification |
| Рамки, фальц, уменьшение в ImageMagick | нет прямой замены в этом аудите | Оставить, поверх растра callas. Перенести на бокс потребуются реальные координаты TrimBox |
| Превью исходников TIFF/JPEG/PNG | не заменяется напрямую | Либо остаётся ImageMagick, либо идёт после конвертации в PDF, что меняет смысл превью «независимо от сборки» (`batch_processor.py:850-852`) |
| Лист возврата, FTP, кэш, эндпоинты | не относится к callas | Остаётся |

**Точка внимания:** превью синхронно зависят от отдельного сервера. Сейчас ошибка превью не валит заказ (`batch_adapter.py:311-325`). Рекомендуется сохранить это свойство и хранить gs как резервный рендер только при явном решении, поскольку резервный рендер может выглядеть иначе [предложение].

В ветке `codex/callas-pdf` по записи этапа callas уже есть `core/callas_toolbox.py`, её содержимое здесь не проверялось.

## 6. Требует отдельного решения заказчика

1. Нужен ли TIFF вообще, и если да, для кого, с каким разрешением и цветовым пространством.
