План сервера callas

Инструкция для подключения выделенной VM с pdfToolbox CLI к Image Magic. Точки подключения сверены с текущим кодом 1 ноября 2026 года. Лицензия активирована, доступно 8 потоков.

Что строим

  • Callas делает две операции: объединяет страницы PDF и рендерит PDF в PNG для превью.
  • ImageMagick по-прежнему создаёт страницы PDF, наносит рамки и сохраняет WebP.
  • PitStop .ppp проверяет PDF, собранный callas. Его интеграция не меняется.
  • Статусы, перемещение файлов, Sborka и публикация остаются в приложении.
sequenceDiagram
  participant A as Image Magic
  participant S as Шара /mnt/shared
  participant C as Служба callas
  participant P as PitStop
  A->>S: страницы PDF в .callas/job_id/in
  A->>C: PUT /jobs/job_id merge
  C->>S: копия на локальный диск со сверкой SHA
  C->>C: pdfToolbox --mergepdf
  C->>S: результат и SHA в .callas/job_id/out

  A->>S: сверка SHA и страниц, контроль gs, replace в PDF/
  A->>P: проверка как сейчас
  A->>C: PUT /jobs/job_id render
  C->>S: PNG страниц
  A->>A: рамки ImageMagick и WebP в Previews/

До начала

  1. Смените production-пароль из deploy.py:15 и настройте SSH по ключу.
  2. Заведите тестовый клон на отдельной машине. На 10.20.2.104 pytest работает с рабочей БД.
  3. Исправьте в services/coordinator.py сравнение текста таймаута (:788, :811) и отсчёт таймаута от постановки в пул (:719). Удалённая очередь сделает эти дефекты заметнее.

Часть 1. Что сделать на сервере callas

1. Подготовить систему

sudo useradd --system --create-home --shell /usr/sbin/nologin callas
sudo mkdir -p /opt/callas-service /var/lib/callas/{work,cache} /var/log/callas
sudo chown -R callas:callas /var/lib/callas /var/log/callas
sudo apt-get install -y python3-venv cifs-utils fontconfig libatomic1

Рабочий диск должен быть локальным. Для старта закладывайте минимум 200 ГБ и проверьте по замерам: заказы бывают до 2000 МБ, а в кадре одновременно до 8 заданий.

2. Смонтировать ту же шару

Путь на VM должен совпадать с приложением, иначе нужна подмена путей. Приложение работает через /mnt/shared, это //192.168.88.100/shared.

//192.168.88.100/shared /mnt/shared cifs credentials=/etc/callas-smb.cred,uid=callas,gid=callas,vers=3.0,hard,_netdev,x-systemd.automount 0 0

Файл учётных данных: права 600. Служба пишет только в .callas/. Исходники защищаются правами SMB-пользователя или вторым монтированием ro.

3. Проверить CLI под пользователем службы

sudo -u callas pdfToolbox --cachefolder=/var/lib/callas/cache/w1 --status
pdfToolbox --help mergepdf
pdfToolbox --help saveasimg

Зафиксируйте в документе: версию, поддержку 8 процессов, параметры --imgformat, --resolution, --outputfolder, шаблон имён PNG и поведение --optimizepdf и --nooptimization.

Лицензию активировали с --cachefolder, поэтому проверьте, нужна ли она в каждой папке кэша. Безопасность одной папки для параллельных процессов не подтверждена. Если нужен один кэш, сначала проверьте его под нагрузкой из 8 процессов.

4. Развернуть службу заданий

Это маленькое приложение на Python и FastAPI в отдельной папке callas_service/ нашего репозитория. Адрес предлагаю такой: порт 8765, доступ только с 10.20.2.104.

ЗапросНазначение
PUT /jobs/{job_id}Создать merge или render. Повтор с тем же ID не запускает работу заново
GET /jobs/{job_id}Статус, код выхода, файлы, SHA, stderr и длительность
DELETE /jobs/{job_id}Отменить задание и завершить группу процессов
GET /healthВерсия, свободные слоты, шара, диск
  • 8 потоков: общий семафор на 8 процессов. Очередь хранится в SQLite на локальном диске, чтобы пережить рестарт.
  • Приоритет: слияние идёт раньше превью, потому что заказ без PDF не продолжит работу. Держите для слияния минимум 2 слота из 8.
  • Задание: вход копируется на локальный диск и сверяется по SHA, callas работает локально, результат пишется на шару как .tmp и переименовывается.
  • Безопасность: токен в заголовке Authorization, проверка путей внутри /mnt/shared, запуск без shell=True.
  • Коды выхода: до --help успехом считается только 0 при наличии результата. Всё остальное приходит как сбой со stderr.
  • Сроки: служба сама ограничивает выполнение: слияние 600 с, рендер 300 с. Значения стартовые, уточнятся по замерам.
  • Очистка: локальный диск после задания, .callas/ на шаре через 24 часа.
# /etc/systemd/system/callas-service.service
[Service]
User=callas
WorkingDirectory=/opt/callas-service
EnvironmentFile=/etc/callas-service.env
ExecStart=/opt/callas-service/.venv/bin/uvicorn callas_service.app:app --host 0.0.0.0 --port 8765 --workers 1
Restart=always
KillMode=control-group
TimeoutStopSec=60
LimitNOFILE=65536

Нужен строго один worker: иначе лимит 8 будет считаться в каждом процессе отдельно.

5. Закрыть сеть и настроить наблюдение

sudo ufw allow from 10.20.2.104 to any port 8765 proto tcp
sudo ufw allow OpenSSH
sudo ufw enable

Перед ufw enable убедитесь, что не закроете себе SSH. Логи пишутся в /var/log/callas с ротацией. Следите за свободным местом и длиной очереди.

Новый модуль services/callas/

  • engine.py: интерфейс merge(pages, target) и render(pdf, out_dir, dpi), локальная реализация поверх текущего кода.
  • client.py: HTTP-клиент, опрос статуса, отмена, понятные ошибки на русском.
  • paths.py: проверка, что файл внутри /mnt/shared, по образцу services/pitstop/paths.py.

Если входная папка вне шары, задание должно завершаться понятной ошибкой. Страницы для слияния сначала копируются в .callas/<job_id>/in/, потому что сейчас они создаются во временной папке приложения.

IMAGE_MAGIC_PDF_MERGE_ENGINE=pymupdf        # затем callas
IMAGE_MAGIC_PREVIEW_RENDER_ENGINE=ghostscript  # затем callas
IMAGE_MAGIC_PREVIEW_FORMAT=png              # затем webp
IMAGE_MAGIC_CALLAS_URL=http://<адрес-VM>:8765
IMAGE_MAGIC_CALLAS_TOKEN=...                # только в настройках службы
IMAGE_MAGIC_CALLAS_SHARED_ROOT=/mnt/shared

Важные условия

  • Параллельность заказов на сервере приложения равна числу ядер. Лимит callas 8 должен держать очередь службы, поэтому время ожидания не входит в срок выполнения.
  • Таймаут клиента должен быть больше суммы очереди и выполнения, а поздний ответ отсекается по job_id.
  • PNG из callas должен содержать фактический DPI, потому что от него зависят рамки. Если записи DPI нет, движок передаёт значение явно.
  • Если callas недоступен, заказ получает понятную ошибку и может быть запущен повторно. Автоматического перехода на старый движок нет: движок меняют только настройкой.
  • Проверьте WebP в ImageMagick: magick -list format | grep -i webp.

Порядок запуска

  1. Ручной стенд. Прогоните 20–50 реальных PDF вручную и сравните страницы, боксы, ICC и размер с PyMuPDF и Ghostscript.
  2. Служба и тесты. Поддельный CLI в тестах службы, поддельная служба в тестах приложения. Настоящая VM в тестах не используется.
  3. Нагрузка. 8 параллельных процессов, большие файлы, отключение шары, kill службы, отмена и повтор с тем же job_id.
  4. Тень превью. Рабочий результат остаётся за Ghostscript, callas рендерит рядом для сравнения.
  5. Переключение превью. Сначала callas и PNG, затем WebP, отдельным шагом.
  6. Тень слияния. Собираем обоими движками и сравниваем страницы, боксы и результат PitStop.
  7. Переключение слияния. Сначала digital, потом offset.

Откат: вернуть значения pymupdf, ghostscript, png и перезапустить fastapi-app. Старый код удаляется только после полного рабочего цикла без откатов.

Предлагаемые критерии приёмки

  • Совпадают число и порядок страниц, размеры с допуском 0,5 pt, TrimBox и BleedBox.
  • Результаты PitStop не хуже, чем у текущей сборки.
  • Превью WebP дают замеренное уменьшение объёма без потери читаемости рамок.
  • После kill службы, рестарта и обрыва шары нет ни одного ложного passed и ни одного подменённого файла.

Что осталось проверить и получить

  • Адрес VM, пользователь SSH, путь к CLI и версия Ubuntu.
  • Есть ли сетевой путь 10.20.2.104 → VM:8765 и доступ VM к шаре.
  • Флаги --saveasimg взяты из старой ветки и пока не сверены с --help.
  • Лицензия: действуют ли 8 потоков как 8 одновременных CLI-процессов. Если они относятся к одному процессу, схема слотов изменится.
  • Атомарность rename на CIFS и поведение callas с общей папкой кэша.
  • Что должно сохраняться в итоговом PDF: Output Intent, слои, XMP, PDF/X.
