Image Magic: PDF-аудит и переход на callas

Обзор работы сервера и этапов PDF. Основа: шесть отчётов в docs/pdf-audit/, снимок на 1 ноября 2026 года. Код не менялся.

Сначала сделать это

Пароль SSH/sudo от production лежит открытым текстом в deploy.py:15, и файл опубликован в публичном DMIYTRO/fast-api-for-ubuntu. Смените пароль: удаление из git его уже не защитит.

Запасной Argon2-хеш тестового пароля находится в server/settings.py. Переменная IMAGE_MAGIC_PASSWORD_HASH в настройках службы не найдена, поэтому production, вероятно, использует его. Это предположение, его нужно проверить.

Этот каталог и есть production на 10.20.2.104. pytest здесь импортирует control_panel с рабочей БД, поэтому полный прогон тестов на этом хосте опасен.

Главные выводы

  • Callas не заменит всё. Решение: он заменит только слияние и рендер PDF. Растр в PDF, ресэмплинг, рамки, превью исходников и лист возврата остаются на ImageMagick, проверка остаётся на PitStop .ppp, PyMuPDF остаётся независимым контролем.
  • Самые опасные дефекты не в PDF. Они в координаторе и перемещении файлов, и callas их не исправит. Их нужно закрыть до подключения.
  • TIFF как результат превью в коде не создаётся. Сейчас путь такой: PDF, затем PNG через Ghostscript на 150 DPI. TIFF бывает только на входе.
  • Без PitStop оператор видит превью исходников, а не печатаемого PDF. PitStop по умолчанию выключен.
  • Лицензия callas может быть недействительной. По гиду тестовая истекала 16 сентября 2026 года. Текущий статус не проверялся.

Целевая схема с callas

Рекомендация: тонкая HTTP-служба заданий на отдельном Linux-сервере запускает CLI, файлы идут через CIFS-шару. SSH отклонён: нет постоянного ID задания и надёжной отмены. Hotfolder отклонён из-за слабой диагностики и связи результата только по именам. Режим --server можно поставить внутрь службы позже, если подтвердится его поведение.

flowchart LR
  subgraph APP[Сервер приложения]
    C[RunCoordinator] --> AD[ProcessorAdapter без изменений]
    AD --> PE[Порт PdfEngine: слияние и рендер]
    PE --> V[Сверка SHA, PyMuPDF, публикация replace]
  end
  subgraph CAL[Сервер callas]
    S[HTTP-служба заданий] --> L[Локальный диск]
    L --> CLI[pdfToolbox CLI]
  end
  PE -->|job_id, срок, отмена| S
  SH[(CIFS-шара: исходники только чтение)] --> L
  CLI --> OUT[(.callas/job_id/)]
  OUT --> V
  V --> PS[PitStop .ppp: проверка без изменений]
  • job_id складывается из хеша операции, SHA входов, параметров, хеша профиля и версии движка, поэтому поздний результат отсекается.
  • Растр в PDF по-прежнему делает ImageMagick на сервере приложения, callas получает готовые страницы PDF.
  • PitStop проверяет итоговый PDF, собранный callas. Сбой проверки никогда не должен давать passed. Нужно добавить настоящую повторную проверку, сейчас её нет.
  • Для сборки автоматического отката на локальный движок нет.

Порядок работ

  1. Безопасность. Сменить пароль, убрать секреты и файлы заказов из git, проверить репозитории, закрыть порт 8000 снаружи.
  2. Защита данных. Настроить резервные копии SQLite, порог по диску и отдельную среду для тестов.
  3. Координатор. Исправить таймауты, поздний результат, блокировку подтверждений, живучесть потока и блокировку папки.
  4. Файлы. Добавить манифест перемещений, безопасный replace, сверку SHA и проверки до Sborka.
  5. Логика проверки. Исправить расчёт DPI, /Rotate, парсер отчётов и добавить настоящую повторную проверку.
  6. Callas, этапы 0–7. План нужно сократить: этапы профилей и тени preflight больше не нужны. Остаются основания, ручной стенд, порт, тень слияния и рендера, переключение по одной операции, вывод старого кода для этих двух операций. Сначала digital, потом offset.

Каждый этап callas откатывается настройкой. PitStop остаётся постоянным финальным допуском. Ветку codex/callas-pdf как есть не вливать: она позади main и меняет файл после контроля.

Нужны ваши решения

  1. Подтвердите, что «Canvas PDF Toolbox» это callas pdfToolbox. Какая лицензия: CLI или Server, с каким лимитом параллельности?
  2. Роль превью: только компоновка или ещё и цветовое решение? От этого зависит качество сжатия WebP.
  3. Что должно сохраняться в итоговом PDF: боксы, Output Intent, PDF/X, слои?
  4. Что делать при недоступности callas: остановить обработку или держать резервный путь?
  5. Кто забирает файлы из PDF/Print/, и идемпотентна ли отправка в Sborka?

Границы проверки

  • Реальные заказы, PitStop, callas, Sborka и слоёные TIFF из Photoshop не проверялись. Опыты шли на синтетических файлах и подставных адаптерах.
  • Статистика взята из снимка БД без WAL и приблизительна.
  • Флаги callas взяты из ветки, с --help не сверялись. Атомарность rename на CIFS не проверена.
  • gh на хосте нет, GitHub смотрели через анонимный публичный API. Рабочий origin: fast-api-for-ubuntu, а не Image-Magic.
  • Отчёт 06 учитывает отчёт 05 только частично, потому что тот появился позже.
