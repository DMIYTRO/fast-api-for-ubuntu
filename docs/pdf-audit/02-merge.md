# Этап merge: объединение PDF и путь файлов до печати

Метки: **[код]** — проверено чтением текущего рабочего дерева; **[опыт]** — воспроизведено в scratch на PyMuPDF 1.28.0 из `.venv`, на синтетическом PDF; **[предп.]** — предположение, не проверено. Тесты проекта и production не запускались.

Серьёзность: S1 — брак в печати или потеря файлов; S2 — рассинхронизация, ручной разбор; S3 — неудобство, мусор.

## 1. Как работает пошагово

### 1.1. Сборка производственного PDF (при проверке)

1. `BatchProcessor.create_pdfs` обрабатывает только `order.passed` (`processing/batch_processor.py:483-488`).
2. Порядок: один двухстраничный файл идёт как есть, иначе сортировка «face первым» (`:516-520`). Файл без стороны считается face (`:43-45`).
3. Имя итога — stem face-файла (`:523-528`), путь `PDF/<stem>.pdf` (`:490`).
4. Временная папка создаётся внутри `PDF/`: `.{order_id}_*` (`:492-495`).
5. `_prepare_page_pdfs`: входные PDF берутся без изменений; растры при необходимости ресэмплируются и конвертируются через `magick` без сжатия (`:568-607`, `core/pdf_exporter.py:13-38`).
6. `merge_pdfs_with_pymupdf`: проверка наличия и непустоты входов, `insert_pdf`, `save`, повторное открытие и сверка числа страниц (`core/pdf_exporter.py:79-134`).
7. `_validate_created_pdf`: рендер gs в 72 DPI, сверка числа страниц, размера и порядка (`batch_processor.py:609-666`).
8. Атомарный `replace` в итоговое имя (`:509`). Ошибка уходит в результат заказа и копирует исходники в `Troubles/<order_id>/` с `.error.txt` (`services/batch_adapter.py:243-259`, `batch_processor.py:706-728`).
9. Далее PitStop-проверка (ревизия 1) и превью по итоговому PDF в `Previews/Final/<aggregate>/r0001/` (`batch_adapter.py:262-301`).

### 1.2. Отправка в печать

1. `POST /api/orders/prepare-print` → `OrderWorkflowService.prepare` (`control_panel.py:1241-1245`, `1224-1236`). Маршрут вызывает `prepare` синхронно; `OrderWorkflowService.submit` (`order_workflow.py:164`) вне тестов не вызывается (grep).
2. Заказы читаются снимком до захвата блокировок (`order_workflow.py:239-242`).
3. При нескольких заказах без layered TIFF сразу вызывается пакетная отправка в Sborka (`:288-295`), до всех локальных проверок.
4. По каждому заказу: проверка неоднозначности, статуса и готовности PitStop (`:306-354`), поиск `OrderResult`, блокировка в памяти, поиск pending-действия, идемпотентность, проверка перехода (`:355-445`).
5. Запись `OrderAction(pending)` с защитой уникальным индексом (`:465-496`, `server/models.py:311`).
6. Если есть layered TIFF: `build_reviewed_layered_print_pdf`, `inspect_pdf`, повторный PitStop, новая ревизия и sha256 (`:502-562`).
7. `FileLifecycle.accept_for_print`: исходники → `Processed/`, PDF → `PDF/Print/`, превью → `Previews/Processed/` (`services/file_lifecycle.py:63-77`). Эти папки создаются при первом реальном перемещении.
8. `apply_file_transition` сохраняет статус и пути (`services/coordinator.py:364-419`).
9. Одиночная отправка в Sborka (`order_workflow.py:655-658`). Sender передаёт только номер заказа и комментарий (`services/sborka_integration.py:54-66`); путь PDF не передаётся.
10. `OrderAction=prepared`. При исключении на шагах 8-10: откат файлов, восстановление снимка, `failed` (`order_workflow.py:689-711`).

### 1.3. Layered TIFF (`services/layered_tiff_print.py`)

1. Нет layered TIFF — функция возвращает `None`, используется обычный путь (`:82-88`).
2. Для каждого layered-файла ищется `PDF/<stem>_layered-composite.pdf`. Если его нет — создаётся черновик с превью, отправка затем останавливается (`:113-126`, `:209-215`).
3. Части всех файлов пишутся в `PDF/Print/Parts/NN_side_stem.pdf`: обычные страницы из производственного PDF, layered из экспорта (`:166-207`).
4. Размер сравнивается с производственным с допуском 0,5 pt — только если производственный PDF есть (`:187-196`).
5. Части собираются в `PDF/<prod>_reviewed-layered.pdf` через временный файл (`:217-257`), и этот файл идёт в `accept_for_print`.

### 1.4. Возврат

`return_for_rework` переносит всё найденное в `Troubles/<order_id>/`, идентичные дубликаты схлопываются (`file_lifecycle.py:79-99`). Переход `accepted_for_print → returned_for_rework` разрешён (`services/domain.py:66`).

### 1.5. Что не участвует в этом пути

- `core/pdf_builder.py` — только PDF-отчёт ReportLab, к производственному файлу отношения не имеет.
- `services/postpress.py` — только разбор текста Sborka в метаданные сгибов; файлов не трогает. Влияет лишь на overlay превью (`batch_adapter.py:139`).

## 2. Нюансы

- Мест сборки два: `merge_pdfs_with_pymupdf` и `layered_tiff_print.py`. Вторая использует свой `insert_pdf` со своими проверками, `garbage=3, deflate=True`.
- **[опыт]** `insert_pdf` с параметрами по умолчанию сохраняет TrimBox и BleedBox страницы, но теряет `/OutputIntents`, `/OCProperties` (слои), XMP и title. Итог проекта по этой причине не является PDF/X, даже если вход им был. Проверено на одном синтетическом файле; реальные заказы не проверялись.
- **[код]** gs запускается без `-dUseCropBox`/`-dUseTrimBox`, поэтому контроль размера идёт по умолчанию gs (**[предп.]** MediaBox), а сверка размера в layered — по `page.rect` (CropBox с учётом поворота).
- **[код]** Производственный PDF после отправки layered-заказа остаётся в `PDF/`, в БД указан reviewed-файл. Это задокументировано (README:331).

## 3. Что ломает работу с файлами

### S1

**M1. Вынужденная печать ошибочного заказа не может завершиться.** [код]<br>
`prepare` пропускает с `confirm_failed_processing` (`order_workflow.py:341-345, 432-436`), но `apply_file_transition` проверяет переход без этого флага (`coordinator.py:385`), а для `error` в таблице разрешён только возврат (`domain.py:65`). Сценарий: оператор нажимает «всё равно в печать» → файлы переезжают → `ValueError` → откат → ошибка. Если PDF нет, падает ещё раньше на `_required_path` (`file_lifecycle.py:69`). Тест проходит только из-за `FakeCoordinator` без проверки (`tests/test_order_workflow.py:66-73, 225-239`). Вывод сделан чтением, сквозным прогоном не подтверждён. По серьёзности это отказ функции, а не брак.

**M2. Пакетная отправка в Sborka идёт раньше всех локальных проверок.** [код]<br>
`order_workflow.py:295` вызывается до проверки статуса, PitStop, блокировок и файлов. Сценарий: выбрано 5 заказов, один не прошёл PitStop или конфликтует по имени. Sborka получила все 5, локально этот заказ остался не отправленным, откатить внешний вызов нельзя. При сбое перемещения откат файлов не отменяет отправку. Если Sborka вернула ошибку, исключение прерывает весь `prepare`, ответа по заказам нет.

**M3. Потеря файла при `conflict_strategy="replace"`.** [код]<br>
`destination.unlink()` выполняется на этапе планирования (`file_lifecycle.py:186-187`), до единого перемещения. Сценарий: заменяем `Processed/x.tif`, следующий `move` падает (права, место). Старый файл удалён безвозвратно, откат его не вернёт, сообщение обещает откат «всё или ничего».

**M4. Удаление исходника без сравнения.** [код]<br>
`file_lifecycle.py:200-209`: если цель появилась между планированием и перемещением, обе ветки делают `source.unlink()`; ветка `else` — без проверки идентичности. Сценарий: два действия или внешний процесс создали одноимённый файл в окне гонки; исходник стёрт, а файл в цели может быть другим. Вероятность низкая, ущерб — потеря исходника.

**M5. «Просмотрено оператором» определяется только существованием файла.** [код]<br>
`layered_tiff_print.py:113`: есть `_layered-composite.pdf` — считается проверенным. Факт просмотра нигде не записывается, сверки с TIFF по времени или хешу нет. Сценарий 1: черновик создан, оператор нажал «в печать» повторно, не открыв его — черновик уходит в печать. Сценарий 2: клиент заменил TIFF, а старый экспорт остался — печатается старое изображение. README:323 утверждает обратное («непроверенный экспорт не попадает»).

**M6. Если все файлы layered и производственного PDF нет, размер не проверяется.** [код]<br>
`layered_tiff_print.py:145-147, 187`: сверка размера идёт только при `base is not None`, а экспорт `magick` не применяет ресэмплинг и поворот заказа. Сценарий: TIFF нужно было повернуть или подогнать — итог другого размера. Остаётся `inspect_pdf` и PitStop; что именно они ловят в этом случае — вопрос этапа verification. Без PitStop защиты, вероятно, нет [предп.].

**M7. Содержимое Face/Back не проверяется, проверка порядка тавтологична.** [код]<br>
`batch_processor.py:662-666` сравнивает `expected_side` с номером страницы, но оба следуют из той же сортировки. Сторона определяется только именем файла. Сценарий: клиент перепутал `_face` и `_back` — проверка пройдёт. Защита только в просмотре превью.

**M8. Разный размер сторон — предупреждение, не ошибка.** [код]<br>
`batch_processor.py:466-470`: несовпадение фактических форматов только в warning. Каждая страница сверяется лишь со своим ожидаемым размером (`:649-655`), друг с другом — нет, с допуском не менее 0,6 мм. Точное влияние зависит от правил профиля (этап generation/verification).

**M9. Потеря OutputIntent и слоёв при слиянии.** [опыт]<br>
См. раздел 2. Для входных PDF с OutputIntent итог теряет условие печати. Значимо, если типография на него опирается.

### S2

**M10. Рестарт после смены статуса, но до Sborka, отмечает заказ отправленным.** [код]<br>
Шаг 8 сохранён, процесс упал до `prepress_sender` → `recover_interrupted_runs` видит конечный статус и файлы на месте → `prepared` (`services/sql_repository.py:526-531`). Следующая попытка получает `idempotent` (`order_workflow.py:419-430`). В Sborka заказ не ушёл, в интерфейсе выглядит отправленным.

**M11. Рестарт посреди перемещения оставляет заказ разобранным.** [код]<br>
Манифеста перемещений нет, docstring это признаёт (`sql_repository.py:503-506`). Часть файлов в `Processed/`, БД указывает старые пути, повтор падает на «Не найден…». `FileTransition.moves` живёт только в памяти.

**M12. Таймаут Sborka с неизвестным исходом.** [код]<br>
Таймаут 20 с (`sborka_integration.py:38`). Ответ потерян, а заказ принят: откат файлов и статуса (`order_workflow.py:689-706`), локально снова «готов». Повтор отправит заказ второй раз. Идемпотентность на стороне Sborka неизвестна [предп.]. То же при сбое `session.commit` после успешной отправки (`:681`).

**M13. Откат может быть неполным, и это не видно оператору.** [код]<br>
Ошибки отката внутри `_move_all` молча проглатываются (`file_lifecycle.py:222-223`). Ошибка `rollback` только логируется (`order_workflow.py:696-702`), при этом `restore_order_snapshot` в том же `try` пропускается: файлы и БД расходятся, оператору показана обычная ошибка.

**M14. Частичное наложение очередей в неиспользуемом `submit` (латентно, S3).** [код]<br>
`order_workflow.py:169-179`: в очередь проверяется пересечение ключей, но `_run_background` получает полный `command`. Сценарий `[A,B]` и `[B,C]`: B обрабатывается и вторым заданием, пакетный вызов Sborka получит B дважды. Сейчас не проявляется: `submit` вне тестов не вызывается (мёртвый путь). Станет дефектом при его подключении.

**M15. Устаревший снимок заказа.** [код]<br>
Снимок читается до блокировки (`:239-242`). Второй запрос после завершения первого видит старый статус и получает ложную ошибку «не найден файл» с записью `failed`. Двойного перемещения нет: `_source_paths` останавливает.

**M16. Пересоздание PDF при перезапуске проверки.** [код]<br>
`temporary_output.replace(output_path)` молча заменяет `PDF/<stem>.pdf` (`batch_processor.py:509`); то же для reviewed-файла (`layered_tiff_print.py:254`) и частей (`:201`). Если старый запуск ещё не отправлен, его ревизия и sha уже относятся к другому файлу. Перед печатью sha файла не сверяется: `pitstop_ready` сравнивает только номера ревизий (`order_workflow.py:325-329`), а `accept_for_print` не читает файл.

**M17. Обязательные превью блокируют печать.** [код]<br>
`_required_paths` падает на пустом списке (`file_lifecycle.py:145-149`), хотя при `generate_previews=False` заказа без превью быть может. Сбой превью не должен останавливать перемещение годного PDF — или это явное решение.

**M18. Копия в Troubles живёт отдельно от Processed.** [код]<br>
Копии из `copy_pdf_failure_to_troubles` не удаляются при последующей успешной обработке того же имени. `Troubles/` постепенно перестаёт отражать текущие проблемы.

**M19. Возврат после отправки не отменяет печать.** [код]<br>
`accepted_for_print → returned_for_rework` разрешён. Файлы уходят в Troubles, но `rework_sender` — отдельный запрос; что он делает с уже переданным в препресс заказом, по коду не видно [предп.]. Части и reviewed в Print/Parts остаются.

- **M24.** Разные умолчания стороны: `_logical_side` даёт face (`batch_processor.py:45`), а `layered_tiff_print.py:93` файл без стороны сортирует вторым. Для валидных заказов сейчас не проявляется, но логика задублирована.

## 5. Улучшения стабильности

Порядок — по отношению пользы к объёму.

1. Передать `confirm_failed_processing` в `apply_file_transition`, тест на настоящем `RunCoordinator` (M1).
2. Вынести пакетную отправку после локальных переходов; отправлять только успешно подготовленные (M2).
3. Заменить `unlink` на переименование в резервный файл с удалением после успеха (M3); в `_move_all` сравнивать файлы или падать (M4).
4. Журнал перемещений в БД до первого `move`: основа восстановления после рестарта (M11).
5. Отдельное состояние «Sborka не подтвердила». `prepared` — только при сохранённом ответе (M10, M12).
6. Запись факта просмотра: file_id, sha TIFF, sha экспорта, оператор, время (M5).
7. Сверка sha256 перед перемещением с текущей ревизией (M16).
8. Сверка размера layered с размером заказа при отсутствии производственного PDF (M6).
9. Единая функция сортировки и один модуль слияния (M24).
10. Показывать оператору неполный откат отдельным статусом (M13).
11. Перевыпуск ревизий вместо перезаписи одного имени (M16).

## 6. Что заменяется в callas

| Сейчас | Кандидат в callas | Комментарий |
|---|---|---|
| `merge_pdfs_with_pymupdf` | Слияние pdfToolbox [предп.: точный режим подтвердить на этапе callas] | Выгода: возможно сохранение OutputIntent; проверить на реальных файлах |
| `insert_pdf` в layered | То же или оставить извлечение страниц | Лучше единая реализация |
| `magick` → PDF страницы | Этап generation | Вне этого этапа |
| Контроль 72 DPI gs | Отчёт Preflight по боксам | Точнее, чем размер рендера; локальный минимум оставить |
| Второй PitStop по reviewed | Второй прогон профиля | Семантика сохраняется |

**Не заменяется, остаётся в приложении:** порядок Face/Back, `FileLifecycle`, статусы, журнал, откаты, Sborka, ревизии и sha. callas не решает M1-M5 и M10-M16.

Новые риски отдельного сервера: передача файлов по сети, таймаут с неизвестным исходом, повтор операции, частичный файл в общей папке. Запись результата — только через временное имя и `replace` на той же ФС. Подробности у этапов callas и stability.

## 8. Ответ на вопрос callas

Других мест сборки страниц нет: `insert_pdf` найден только в `core/pdf_exporter.py:104` и `services/layered_tiff_print.py:197, 236` (grep по `*.py`). Обязательные требования к сохранению в коде не зафиксированы. Сейчас боксы сохраняются, OutputIntent, OCG и XMP теряются [опыт].
