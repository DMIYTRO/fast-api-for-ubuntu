# Этап 04. Проверка PDF

> **Актуальные решения заказчика (важнее текста ниже, где он расходится):**
> растр в PDF остаётся на ImageMagick; проверка остаётся на PitStop `.ppp`, перевод в `.kfpx` не нужен;
> callas заменяет только объединение PDF и генерацию превью из PDF;
> путь превью: callas выдаёт PNG, ImageMagick наносит рамки и сохраняет WebP; TIFF как результат превью не нужен.

Основа: текущие файлы рабочего дерева. Метки достоверности:

- **[код]** прочитано в коде;
- **[проба]** воспроизведено локально в scratch на PyMuPDF 1.28.0 и `gs`, без обращения к PitStop, FTP, Sborka и production;
- **[предположение]** зависит от внешней системы или данных и в коде не подтверждается.

Настоящий PitStop не запускался. Содержимое `.ppp`, реальный формат отчёта и данные production неизвестны.

## 1. Как работает проверка

### 1.1. Входной PDF (до сборки)

1. `iter_inspect_orders` разбирает имя файла и группирует по клиенту и заказу. PDF идёт в `_inspect_pdf_file`, минуя ImageMagick (`processing/batch_processor.py:106-130`, `:193`).
2. `inspect_pdf` открывает файл через PyMuPDF и не изменяет его. Ошибки: файла нет, он не файл, пустой, не открывается, требует пароль, потребовал ремонта, 0 страниц, больше 2 страниц, страница не читается (`core/pdf_inspector.py:155-192`). Предупреждений не формирует: список `warnings` всегда пуст (`:154`).
3. Собираются боксы, поворот, изображения и тип содержимого (`:123-141`).
4. Сравнения с заказом выполняются в `_inspect_pdf_file` (`processing/batch_processor.py:244-283`):
   - размер MediaBox против «формат из имени + `size_extra_mm`», в обеих ориентациях, с допуском — ошибка;
   - поворот не из 0/90/180/270 — ошибка;
   - effective DPI изображения ниже минимума — ошибка;
   - имя цветового пространства содержит `RGB` и не содержит `ICCBased` — предупреждение;
   - цветовое пространство неизвестно — ошибка.
5. `_validate_order` проверяет состав заказа: один двухстраничный PDF, цветность, стороны, ориентацию, размеры в именах, клиента (`:392-475`). Для единственного двухстраничного PDF выход происходит на `:426-427`, остальные проверки не выполняются.
6. `_inspection_status` даёт `waiting_confirmation`, `error`, `warning` или `passed` (`services/coordinator.py:1045-1052`). При включённом PitStop `passed/warning` показывается как `processing` (`:647-653`).

### 1.2. Сборка и контрольный рендер

Если `order.passed` истинно (`services/batch_adapter.py:223`), `create_pdfs` собирает страницы, сливает их через PyMuPDF и вызывает `_validate_created_pdf` до `replace` в `PDF/` (`processing/batch_processor.py:503-509`). Контроль: файл непустой, `gs` при 72 DPI отрабатывает с кодом 0, число PNG равно числу страниц, размер каждой страницы в пределах `max(tolerance, 0.6)` мм, порядок face/back (`:616-666`). Сбой контроля уводит заказ в `Troubles` (`services/batch_adapter.py:244-259`).

Повторно `inspect_pdf` по итоговому файлу в этом пути не вызывается. Сверка содержимого с исходником не выполняется: контроль видит только факт рендера, число и размер страниц.

### 1.3. PitStop (report-only)

1. `check_pdf` выполняется под `threading.Lock` (`services/pitstop/service.py:54`, `:58`).
2. Проверка входа, выбор профиля, SHA-256, каталог `input/output_report/pitstop/<uuid>` (`:62-71`). Каталог создаётся на Linux-стороне.
3. Пути PDF и отчётов преобразуются из `/mnt/shared/...` в `//host/shared/...` (`paths.py:12-29`). Путь вне общей папки даёт `SharedPathError`.
4. Команда `powershell.exe ... & 'cli' -input ... -mutator ... -reportJSON ... -reportXML ...` без output-аргумента (`service.py:161-177`) уходит через `ssh` с `BatchMode` и строгой проверкой ключа хоста (`transport.py:52-78`).
5. Ненулевой код завершения считается сбоем. Затем JSON читается с общей папки, парсится, а SHA сравнивается заново (`service.py:89-106`).
6. Успех: каталог отчётов удаляется, результат хранится только в БД (`:120-123`). Ожидаемый сбой: `FAILED`, файлы отчёта остаются (`:107-118`).
7. Вердикт считается только по счётчикам: `errors + critical_failures` — ошибка; `warnings + noncritical_failures` — предупреждение (`models.py:61-84`). `fixes`, `informations`, `signoffs` на вердикт не влияют.
8. После PitStop строится производственное превью именно этого PDF (`batch_adapter.py:272-306`).

### 1.4. Итоговый статус и печать

`_completed_order_status` (`services/coordinator.py:1055-1070`), по порядку:

| Условие | Статус |
|---|---|
| есть `artifacts.errors` или заказ не прошёл | `error` |
| PitStop не завершился | `error` |
| вердикт PitStop `error` | `error` |
| вердикт PitStop `warning` | `warning` |
| есть предупреждения заказа или файлов | `warning` |
| иначе | `passed` |

Отдельное поле `pitstop_status`: вердикт, `technical_error` или `not_checked` (`:815-822`).

Печать разрешена при статусе `passed/warning` и готовом PitStop (`services/order_workflow.py:319-345`). Вторая ветка: `confirm_failed_processing` при статусе `error` (`:341-344`, `services/domain.py:81-86`).

Сборка из просмотренных TIFF: `inspect_pdf` и новый PitStop с ревизией `+1`; непрохождение блокирует отправку (`order_workflow.py:504-561`).

### 1.5. Хранение и UI

- `PitstopCheck` привязан к `PdfRevision`, `PitstopIssue` — к проверке (`server/models.py:174-224`, запись `services/sql_repository.py:724-829`).
- `OrderCard.vue` показывает статус, таблицу параметров, ошибки, предупреждения, отчёты PitStop (`:213`, `:238-269`). `PitStopReport.vue` различает технический сбой и брак PDF (`:25-37`, `:71`).
- Ссылки на отчёты появляются только когда сохранён путь (`control_panel.py:175-190`), то есть практически только при сбое после создания отчёта.

### 1.6. Неиспользуемый код

- `validators/`: `get_validator` никем не вызывается. Снаружи импортируются только типы (`core/pdf_builder.py:14`, `core/report_builder.py:11`). `PDFValidator` всегда пишет «Файл обработан через Ghostscript» (`validators/pdf_validator.py:15-21`). В рабочем процессе это не исполняется. **[код]**
- `batch_inspector.py`: отдельный скрипт, импортов и вызовов в репозитории нет. Вопреки docstring PDF не сканирует (`:108`), норма размера в нём равна факту файла (`:145-146`, `:234`), порог 250 задан константой (`:140`), рамки подписаны иначе, чем в `OrderCard.vue:229-230` (там зелёный — рез, здесь красный — рез). **[код]**
- `core.report_builder.build_reports` экспортируется из `core/__init__.py`, вызовов из рабочего потока поиском не найдено. **[код]**

## 2. Матрица проверок и дублирование

| Проверка | inspect_pdf / _inspect_pdf_file | gs-контроль | reviewed-путь | PitStop |
|---|---|---|---|---|
| Открытие, структура | да | да, итог | да | зависит от профиля |
| Шифрование, 0 страниц | да | косвенно | да | зависит от профиля |
| Максимум 2 страницы | да | точное число | да | не связано с заказом |
| Размер против заказа | да (MediaBox) | да (рендер) | нет | только если задан в `.ppp` |
| Effective DPI | да | нет | нет | зависит от профиля |
| Цвет изображений | частично | нет | нет | зависит от профиля |
| Цвет вектора, шрифты, плашки, TrimBox/BleedBox, overprint | нет (боксы собираются, не сравниваются) | нет | нет | зависит от профиля |
| Лимит размера файла | **нет для PDF** | нет | нет | нет данных |
| Неизменность файла | нет | нет | нет | SHA до и после |

Дублирование: открываемость и страницы проверяются трижды разными движками; DPI и цвет, вероятно, повторно в `.ppp` **[предположение]**. Разные движки — это не только издержки: они дают независимый взгляд, но и разные мнения об одном файле.

## 3. Что ломает работу и нелогично

### Высокая серьёзность

**В1. После сбоя PitStop нет рабочего выхода, а UI обещает другое.** **[код]** UI пишет: «Печать заблокирована до повторной проверки» (`PitStopReport.vue:71`), но поиском не найдено ни эндпоинта, ни действия повторной проверки. Сценарий: SSH недоступен пять минут, заказ получает «Ошибка PDF», остаётся новый запуск всей папки. Кнопка «Отправить в работу» (`ActionBar.vue:33`) доступна для любого `error` (`stores/checks.js:36`), включая технический сбой, и подготовка её пропускает (`order_workflow.py:341-344`, `:432-436`). Но `apply_file_transition` проверяет переход без `confirm_failed_processing` (`coordinator.py:385`), поэтому `error → accepted_for_print` отвергается уже после перемещения файлов на шаге lifecycle (`order_workflow.py:566-572`, `:641`); находку подтверждаю за этапом merge. Откат описан в этапе merge. Итог двойной: принудительная отправка задумана как обход проверки и при этом не завершается. Текст в `ActionBar.vue:44` к тому же говорит об «ошибках проверки» и не сообщает, что проверки могло не быть.

**В2. Очередь на блокировке PitStop съедает таймаут заказа.** **[код]** `submitted_at` ставится при постановке в пул, а не при старте (`coordinator.py:717-719`), таймаут по умолчанию 900 с (`:52`), PitStop строго последовательный, команда до 180 с. Сценарий: большая папка при 15 с на проверку; заказы дальше примерно шестидесятого в очереди получают «Превышено время» при исправной системе, после чего незапущенные задачи отменяются (`:754-757`). Точное число зависит от времени сборки; реальные значения не измерялись.

**В3. Защита от позднего результата не работает.** **[код]** `_process_one` ищет текст «не завершился за» (`coordinator.py:811`), а таймаут пишет «Превышено время обработки заказа» (`:788`). Строки не совпадают, поэтому поток, завершившийся после таймаута, перезаписывает «результат не принят» обычным статусом. Сравнение строк здесь надо заменить флагом.

**В4. Блокировка не глобальна.** **[код]** Комментарий `service.py:50-53` обещает сериализацию, но `service_for` создаёт новый `PitStopService` на каждого адаптера и на каждую повторную проверку (`control_panel.py:523-547`, `order_workflow.py:517`). Сценарий: два параллельных запуска или печать из TIFF во время запуска идут в PitStop одновременно и получают тот самый код выхода 1, описанный в комментарии. Ложные «сбои» при исправном PDF.

**В5. Пустой отчёт считается пройденным.** **[проба]** `{"preflightReport": {}}` даёт `passed`: `_count` подставляет 0 (`parser.py:136`). Отчёт с записью в `errors`, но без `errorsNumber`, тоже даёт `passed` при 1 issue, потому что вердикт не сверяется со списком. Сценарий: смена формата при обновлении PitStop или замена движка на callas с другой схемой превратит все заказы в зелёные. Это наиболее опасный отказ для перехода.

**В6. Report-only и `fixes`.** **[предположение, важность высокая]** Ключ называется `-mutator`, выход не сохраняется, а `fixes` не влияет на вердикт (`models.py:61-67`). Если `.ppp` содержит автоисправления, проблема могла бы считаться исправленной в отчёте и оставаться в файле, идущем в печать. Подтверждение нужно по содержимому `Sborka_2Core.ppp` и пробному запуску. Для callas вопрос становится явным, см. раздел 5.

### Средняя серьёзность

**С1. Ложный отказ при `/Rotate`.** **[проба]** Страница MediaBox 300×600 pt с `/Rotate 90`: `inspect_pdf` даёт 105,8×211,7 мм, а `gs` рендерит 600×300, в том числе после слияния (`/Rotate` сохраняется). Входная проверка проходит, `_validate_created_pdf` падает на `:655` и отправляет заказ в `Troubles`. Причина: ожидание берётся из MediaBox (`pdf_inspector.py:131-132`), а `gs` учитывает поворот. Постраничная вёрстка с поворотом — обычное явление при экспорте альбомных макетов.

**С2. Часть сбоев не становится `PitStopCheckResult`.** **[код]** Обрабатываются только три типа исключений (`service.py:107`). Недоступная шара (`OSError` на `mkdir` или SHA, `:66-69`), исчезнувший PDF (`ValueError`, `:63`), неизвестный профиль (`KeyError`) и `UnicodeDecodeError` от `text=True` (`transport.py:66-71`) уходят в общий `except` адаптера (`batch_adapter.py:311`). Итог: `pitstop=None`, `pitstop_status=not_checked`, запись `PitstopCheck` не создаётся, блок «Технический сбой» не показывается, а текст в карточке «Причины обработки указаны выше. Отчёт PitStop появится после успешного создания итогового PDF» (`OrderCard.vue:256-258`) неверен, потому что PDF создан. Вывод Windows не в UTF-8 **[предположение]** и превращает ненулевой код в такой сбой.

**С3. Нет повтора и различения сбоев.** **[код]** SSH-код 255 показывается как «PitStop Server завершился с кодом 255» (`service.py:95`). Нет разделения: сеть, ключ хоста, сбой CLI, отставание SMB. JSON читается один раз сразу после завершения команды; задержка видимости на шаре **[предположение]** даёт сбой. Временная ошибка никогда не повторяется.

**С4. Таймаут убивает только локальный `ssh`.** **[код]** `subprocess.run` завершает клиента; удалённый процесс при этом явно не останавливается. Останется ли он жить — **[предположение]**, поведение Windows OpenSSH надо проверить. Если останется, следующая проверка пересечётся с ним, а блокировка уже снята.

**С5. Записи без `page` валят весь отчёт.** **[проба]** Находка с `location` без страницы вызывает `PitStopReportError` (`parser.py:113-115`). Заказ становится техническим сбоем из-за одной необязательной координаты. Появление таких записей в отчётах PitStop — **[предположение]**, тесты парсера их не покрывают. Страница также считается нумерованной с нуля по коду, но внешнее подтверждение есть только в тестах проекта.

**С6. PDF проверяется слабее растра.** **[код]** `_inspect_pdf_file` не вызывает `_validate_file`, поэтому для PDF не работают лимит размера файла (`max_file_size_mb`) и `allowed_color_modes` (`:351-373`). Без PitStop вектор не проверяется вовсе.

**С7. RGB с ICC-профилем проходит молча.** **[проба]** `DeviceRGB` даёт предупреждение, а имя `ICCBased(RGB,sRGB built-in)` исключается условием `:275`. Именно так обычно выглядит sRGB-изображение из офисных и веб-источников. CMYK и RGB при этом в строке цвета различить можно, условие просто неверно. Без PitStop заказ получит `passed`.

**С8. Маски и мелкие объекты и мелких объектов.** **[проба]** Трафаретная маска (stencil) 8×8 на дюйм даёт effective DPI 8. В пробе `inspect_pdf` принял её, но `_inspect_pdf_file` выдаст жёсткую ошибку DPI (`:269`). Жёсткую ошибку получит и маленький логотип либо любой объект: порог не учитывает площадь или тип. Изображение под клипом считается целиком, а повёрнутое считается по охватывающему прямоугольнику (`pdf_inspector.py:84-88`, эффект **[предположение по формуле]**).

**С9. `is_repaired` всегда ошибка.** **[код]** `pdf_inspector.py:176-177`. Файл с незначительным дефектом xref, который `gs` и PitStop могут прочитать, отвергается без шанса. Это политика, а не ошибка, но её стоит принять осознанно.

**С10. Владельческий пароль не обнаруживается.** **[проба]** Файл с owner-паролем и запретом всех прав даёт `encrypted=False`, ошибок нет. Как к нему отнесётся следующий инструмент, неизвестно.

**С11. Заголовок и причина расходятся.** **[код]** Технический сбой даёт статус `error` с меткой «Ошибка PDF» (`OrderCard.vue:56`, `:213`), а панель ниже утверждает, что PDF не признан бракованным. Метка `technical_error` в словаре есть, но `_completed_order_status` такой статус не возвращает. Также при сбое в БД пишется `verdict=error` (`batch_adapter.py:344`), поэтому статистика по вердикту смешивает брак и сбой.

**С12. Отчёты теряются при успехе.** **[код]** README (`:293`) утверждает, что отчёты сохраняются, а код их удаляет (`service.py:123`). Спор с клиентом или аудит профиля по прошедшему заказу невозможен, остаются только разобранные issue. Обратная сторона: каталоги сбоев не чистятся и копятся. Пустой каталог остаётся и при `SharedPathError`, потому что `mkdir` выполняется раньше `_map`.

**С13. Неверная причина при критических сбоях.** **[код]** `order_workflow.py:534-554` смотрит только на `errors`. Если есть лишь `critical_failures`, оператор видит «PitStop не завершил проверку», хотя проверка завершилась.

**С14. Хэш не проверяется при печати.** **[код]** Готовность сверяет номер ревизии, но не SHA файла (`order_workflow.py:319-331`); `current_pdf_sha256` только сохраняется. Подмена файла в `PDF/` между проверкой и печатью не обнаруживается.

**С15. Длинная строка цвета и `String(32)`.** **[код + проба]** `check.colorspace` для PDF имеет вид `ICCBased(CMYK,Artifex CMYK SWOP Profile)`, это 41 символ, а колонка `file_results.colorspace` имеет длину 32 (`alembic/versions/0001_server_foundation.py:94`). SQLite не ограничивает, PostgreSQL отвергнет запись. Какая БД на production, не проверялось.

**С16. Диагностика расходится с сервисом.** **[код]** `diagnose_pitstop.py` дублирует логику (`:90-110`), не оборачивает все ошибки так же, не применяет блокировку сервиса и импортирует приватную `_powershell_command`. Параллельный запуск с рабочим процессом снова даёт конкуренцию из В4. Сравнивать вывод с поведением сервиса надо с этой поправкой.

### Низкая серьёзность

- **Н1.** Сообщения `inspect_pdf` на английском (`pdf_inspector.py:156-192`), хотя AGENTS.md требует русский для оператора. **[код]**
- **Н2.** Пустая страница проходит как `vector` **[проба]** (`_page_content_type`, `:116-120`): нет содержимого — нет находок.
- **Н3.** Двухстраничный PDF с разной ориентацией страниц проходит: `_validate_order` выходит раньше проверки (`:426-427`). Ветка `:420-423` недостижима, потому что страниц всегда 2, а при `back_colors=0` ошибка уже добавлена. **[код]**

### Ответ этапу merge

Неверный размер layered-итога без производственного PDF локально не ловится **[код]**: сравнение размеров есть только при `base is not None` (`services/layered_tiff_print.py:187-192`), `inspect_pdf` размер с заказом не сравнивает (`order_workflow.py:508`). ## 4. Модель SSH + SMB

Сильные стороны **[код]**: белый список профилей, строгая проверка ключа хоста, исключена подстановка путей клиентом, SHA до и после, запись отчётов в новый UUID-каталог.

Слабые места: нет проверки готовности перед запуском (монтирование, SSH, CLI, запись), поэтому при падении сервиса весь PDF собирается и только потом падает; две независимые точки отказа сводятся к одному сообщению; нет повторов и отмены; блокировка живёт внутри объекта; состояние «проверяется» недолговечно. Комментарии говорят о Parallels и Mac, а README — о VM и Linux-пути: названия `mac_shared_*` устарели.

## 7. Что требует отдельного решения

1. **Report-only или Fixup.** Если callas исправляет PDF, появляется новая ревизия, которую надо заново проверять и показывать оператору. Guide предупреждает о проблемах совместного вывода файла и отчёта (`README:115-118`). От этого зависит ответ на В6.
2. **Разрешена ли печать при техническом сбое** и кто вправе (В1).
3. **Какой движок авторитетен**, если локальная проверка и callas расходятся.
4. **Политика серьёзности:** что ошибка, что предупреждение, что информация; соответствие severity callas трём уровням проекта.
5. **Отказ при недоступности callas:** ждать, блокировать запуск или идти без проверки. Рекомендация: блокировать готовность к печати, не пересобирая PDF.
6. **Срок хранения отчётов.**
7. **Судьба старых данных:** исторические `pitstop_checks` и смешанные вердикты.
8. **Параллельная сверка:** прогон PitStop и callas на контрольном наборе до отключения PitStop, сравнение находок по файлам.
9. **Статус лицензии:** по записи этапа callas тестовая лицензия истекала 16.09.2026. Это уже в прошлом относительно даты аудита, актуальное состояние не проверялось.
