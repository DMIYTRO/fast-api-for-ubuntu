# Этап 6. Целевая архитектура callas и план миграции

> **Актуальные решения заказчика (важнее текста ниже, где он расходится):**
> растр в PDF остаётся на ImageMagick; проверка остаётся на PitStop `.ppp`, перевод в `.kfpx` не нужен;
> callas заменяет только объединение PDF и генерацию превью из PDF;
> путь превью: callas выдаёт PNG, ImageMagick наносит рамки и сохраняет WebP; TIFF как результат превью не нужен.

Callas в этом аудите не запускался. Лицензии и активационные файлы не открывались. Использованы `01-generation.md` … `05-stability.md` и `exchange.md`. **Выбор B.**
- Операции здесь занимают минуты, файлы большие, а у текущего кода уже есть проблемы с неизвестным исходом (`G3`, `В2`, `В3`). Значит, нужны задание с постоянным идентификатором, статус и отмена.
- В варианте A всё это пришлось бы писать скриптом на удалённой стороне, то есть получилась бы та же служба, только хуже наблюдаемая.
- D отклонён: синхронный заказ пришлось бы ждать по появлению файлов, а отчёт и результат связывать только по именам.

**Когда пересмотреть:** если callas подтвердит, что `--server`/dispatcher даёт очередь, статус и отмену в нашей лицензии, вариант C заменит CLI *внутри* службы. Контракт для приложения не изменится. Если заказчик запретит свою службу на сервере, запасной вариант это A с удалённым скриптом заданий, а не прямой вызов CLI.

Служба обязана: принимать только перечисленные операции и профили из каталога, запускать команды списком аргументов, не принимать произвольные флаги, не писать секреты в журнал, ограничивать пути корнем задания, слушать только внутреннюю сеть с токеном.

## 5. Форма интерфейса

Шов один, но не `ProcessorAdapter`. Этот протокол (`services/coordinator.py:69-78`) работает на уровне заказа: его оставляем без изменений. PDF-операции вызываются внутри `BatchProcessor` и адаптера, поэтому нужны узкие порты ниже него.

```python
class PdfEngine(Protocol):
    def raster_to_pdf(self, source: Path, target: Path, opts: RasterOptions) -> EngineResult: ...
    def merge(self, pages: Sequence[Path], target: Path) -> EngineResult: ...
    def render_pages(self, pdf: Path, out_dir: Path, dpi: int) -> list[RenderedPage]: ...

class PreflightEngine(Protocol):
    def check_pdf(self, pdf: Path, *, profile_id: str) -> PreflightResult: ...
```

- Реализации: `LocalPdfEngine` (текущие `magick`, PyMuPDF, `gs`) и `CallasPdfEngine`. Выбор настройкой на операцию, не одним флагом.
- `PreflightEngine.check_pdf` повторяет сигнатуру `PitStopService.check_pdf` (`services/pitstop/service.py:56`), поэтому вызовы в `batch_adapter.py:263` и `order_workflow.py:520` почти не меняются.
- Код в `services/callas/` по образцу `services/pitstop/`: `models`, `client`, `parser`, `catalog`, `service`. `SSHTransport` не переиспользуется.
- Новый парсер обязан сверять счётчики со списками: пустой отчёт не должен давать `passed` (`В5`).
- Логика кодов: 0 и 1-8 это выполнено, при наличии результата; 100+ и отсутствие файла это сбой. Значения 9-99 считать сбоем до уточнения **[проверить]**. Перенос `service.py:89` как есть даст сбой на каждом файле с находками.
- DTO и таблицы `pitstop_*` сначала сохраняем, callas подключаем адаптером (`04-verification.md`, раздел 6). Сразу через миграцию добавляем `engine`, `engine_version`, заполняем `profile_version` (сейчас в DTO `None`). Иначе результаты двух движков в БД неразличимы. Переименование таблиц отдельным шагом.

API службы:

```text
POST /v1/jobs            {job_id, op, inputs:[{path,sha256,size}], profile_id, params}
GET  /v1/jobs/{job_id}   queued|running|succeeded|failed|cancelled, exit_code, outputs[{path,sha256,size}], log_tail
POST /v1/jobs/{job_id}/cancel
GET  /v1/health          версия, профили с хешами, срок лицензии, очередь, свободное место
```

## 6. Надёжность

**Передача файлов.** Обмен через шару, потому что исходники уже там. HTTP-загрузка больших файлов не нужна. Схема:

1. Приложение проверяет, что вход на шаре, считает SHA-256 и размер.
2. Служба копирует вход на локальный диск, сверяет SHA. Это защищает от недочитанного файла и от капризов SMB. Гид отдельно предупреждает о сетевых папках.
3. CLI работает только с локальными путями.
4. Результат служба пишет в `<PDF>/.callas/<job_id>/`, закрывает файл, считает SHA.
5. Приложение читает с шары, **само пересчитывает SHA** и проверяет открытие.
6. Публикация выполняет приложение: `replace` в итоговое имя в пределах одной ФС, как сейчас (`batch_processor.py:509`). Атомарность rename на шаре надо проверить (`G17`, этап stability).

Сервер callas получает на шаре запись только в служебные папки. Исходники для него только на чтение, это страховка правила «исходники не меняются». Нужен тот же корень монтирования или явное отображение путей; для Linux-сервера преобразование `paths.py` не требуется **[предп.]**. Требования к локальному диску определить по `max размер × параллелизм × 3` **[предп., уточнить замером]**.

**Идемпотентность.** `job_id = sha256(op, sha входов, порядок, параметры, хеш профиля, версия движка)`.
- Повтор POST с тем же `job_id` возвращает существующее задание, а не запускает новое.
- После рестарта приложение находит задание по тому же ключу.
- Это даёт и кэш: одна и та же проверка не считается дважды.
- Сменился профиль или версия callas: другой ключ, новая проверка. Результат всегда привязан к SHA и ревизии PDF.

**Таймауты.** Разделить три срока: ожидание очереди, выполнение, общий срок заказа. Сейчас таймаут заказа считается с постановки в пул (`В2`), его надо считать с фактического старта; очередь на callas в него не включать. Значения задавать по замерам, а не переносить 180 с от PitStop. Срок выполнения держит служба и завершает всю группу процессов, поскольку простого завершения дочернего процесса мало (`G14`). Клиентский таймаут не означает, что задача умерла: клиент вызывает cancel, затем проверяет статус. Поздний результат публиковать нельзя: перед `replace` проверять, что заказ всё ещё ждёт этот `job_id`, это закрывает `G3`, `В3`.

**Падение сервера.**

| Случай | Поведение |
| --- | --- |
| Сервер недоступен до старта | несколько коротких повторов, затем техническая ошибка оператору; быстрый отказ по `/health`, чтобы вся папка не висела на таймаутах |
| Обрыв при выполнении | опрос по `job_id`; если задания нет, повтор с тем же ключом, ограниченное число раз |
| Служба перезапущена | незавершённые задания при старте `failed: interrupted`, временные папки удаляются |
| Приложение перезапущено | заказ прерывается как сейчас; при повторе `job_id` подбирает готовый результат |
| Лицензия истекла | `/health` показывает заранее; код ошибки отдельно классифицировать [проверить] |
| Сбой PDF или рендера | PDF: ошибка заказа и `Troubles`, как сейчас; превью: ошибка не валит заказ (`batch_adapter.py:311-325`) |
| Сбой preflight | заказ не считается проверенным, **никогда** не `passed` |

Нужна реальная повторная проверка: сейчас после сбоя UI обещает её, а действия нет (`В1`). С отдельным сервером это станет обычным сценарием, поэтому это обязательное условие.

**Автоматического отката на локальный движок при сбое нет** для сборки и проверки: заказ не должен молча получить другой PDF. Для рендера превью резервный `gs` допустим только с пометкой в данных.

**Параллелизм.** Начинать с 1 (`README.md:128-129` гида), поднимать после подтверждения лимита лицензии, замеров памяти и сети. Лимит держит служба: сейчас lock PitStop по экземпляру не работает (`В4`).

**Наблюдаемость.** В журнал: `job_id`, операция, размер, время, код, версии профиля и CLI. Метрики очереди, длительности, сбоев, свободного места, срока лицензии. Папки заданий чистить по возрасту (`G16`).

Тень не должна влиять на заказ: отдельный пул, сбои только в журнал и таблицу сравнения, файлы вне рабочих папок. В сравнении фиксировать: вердикт обоих, классы находок, SHA, страницы, время.

**Откат.** Настройка возвращает `LocalPdfEngine` или PitStop для новых заказов. Уже созданные ревизии остаются, они помечены `engine`. Предупреждение: заказ, собранный одним движком, можно проверять другим, только если ревизия явно отражает это.

## 8. Решение по PitStop

**Решение:** PitStop оставить как финальный допуск на этапах 4-5, переключить на этапе 6, выключить на этапе 7.

Основания:
- заказчик просит заменить обработку на callas, значит цель это один движок, а постоянная двойная проверка удваивает профили (`.ppp` и `.kfpx` автоматически не синхронизируются) и даёт спорящие отчёты;
- но сейчас нельзя отключить проверенный контур, пока нет профилей callas;
- код `services/pitstop/` и `pitstop_*` удалять только после цикла работы без него: исторические отчёты зависят от схемы.

Если заказчик продлевает лицензию PitStop независимо от этого проекта, можно оставить PitStop выборочным контролем. Оговорка: неясно, содержит ли `.ppp` автоисправления (`В6`); это надо выяснить до сравнения.

## 9. Критерии приёмки

Числа это предложение для согласования с заказчиком.

**Сборка:** на эталоне совпадают страницы, порядок, размеры в допуске; нет изменения цветового пространства, ICC и эффективного DPI сверх согласованного; визуальное сравнение без значимых различий; исходники не изменены (проверка SHA).

**Проверка:** 100 % критичных находок PitStop на выборке воспроизведены callas, либо оператор письменно принял расхождение; ноль случаев `passed` у файла с известным дефектом; ложные срабатывания не выше согласованного предела; пустой или повреждённый отчёт не даёт `passed`.

**Превью:** рендер совпадает с печатаемым PDF по SHA; рамки на своих местах; оператор принял цвет.

**Надёжность, обязательные сценарии:** остановка службы на каждом шаге, обрыв сети при записи, заполненный диск, истёкшая лицензия, таймаут, рестарт приложения, двойной запрос, отмена, недоступная шара. Для каждого: нет частичного файла под итоговым именем, нет `passed`, понятное сообщение на русском, повторная проверка работает.

**Производительность:** время заказа не хуже согласованного от текущего, пиковая папка проходит без ложных таймаутов.

**Откат:** выполнен на стенде, занимает минуты, новые заказы идут старым путём.

## Решение заказчика (заменяет противоречащие разделы выше)

Растр в PDF остаётся на ImageMagick, проверка остаётся на PitStop `.ppp`. Callas заменяет только слияние и рендер PDF. Порт `PreflightEngine`, перевод профилей в `.kfpx`, тень preflight и вывод PitStop из работы исключаются.

Дополнение: «рендер PDF» означает генерацию превью из PDF. Она переводится на callas, итоговый формат превью WebP, TIFF не нужен. Поддержка WebP в callas не подтверждена; запасной путь: callas выдаёт PNG, ImageMagick наносит рамки и сохраняет WebP.

Уточнение: путь превью закреплён: callas выдаёт PNG, затем ImageMagick наносит рамки и сохраняет WebP. Вывод WebP из callas не требуется.
