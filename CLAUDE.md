## Commands

No Python linter or formatter is configured, and pytest runs on defaults (no `pytest.ini`/`pyproject.toml`).

```bash
# Single Python test
.venv/bin/python -m pytest tests/test_order_workflow.py -q
.venv/bin/python -m pytest tests/test_order_workflow.py::test_name -q

# Single frontend test (run from frontend/)
npx vitest run src/path/to/file.test.js

# Local server: http://127.0.0.1:8006/login (needs a hash from `manage.py set-password`)
IMAGE_MAGIC_PASSWORD_HASH='...' .venv/bin/python control_panel.py

# Frontend dev server (Vite, proxies the API; run from frontend/)
npm run dev
```

FastAPI serves the built UI from `frontend/dist`, so run `npm run build` to see frontend changes through the backend.

## Architecture

Image Magic is a prepress checker: it validates raster artwork for print orders, groups `face`/`back` files by order, safely corrects small size deviations, builds PDFs and previews, then hands orders off to print or rework.

**Request flow.** `control_panel.py` holds `create_app()`, which wires the routes and all dependencies. `app = create_app()` runs at module level and, unless `initialize_schema=True`, applies Alembic migrations. Importing `control_panel` therefore touches the configured database; tests should call `create_app` with their own settings, repository, and `adapter_factory`.

**Check runs.** `RunCoordinator` (`services/coordinator.py`) runs one check at a time on a worker thread owned by the app lifespan, not by an HTTP request; later runs queue. Orders within a run are processed in parallel by a thread pool. The per-order timeout counts from the moment a worker starts the order, not from queueing, and a timed-out order does not cancel queued ones. A correction needing confirmation pauses only that order, and the run enters `waiting_confirmation` after the others finish. An exception inside one order's processing ends that order as `error` («Сбой обработки заказа: …»), never the whole run. An order with a page-rule violation is never paused for a correction (`_skip_corrections_for_page_rule`): it goes back anyway. An order left `waiting_confirmation` in a finished (failed, interrupted) run can no longer be confirmed, so it may be returned directly; while the run is active, a return of a waiting order is refused with «сначала нажмите «Применить» или «Отклонить»». The UI follows progress over SSE (`GET /api/checks/{id}/events`). Run and order states are defined in `services/domain.py`.

**Layering.** The coordinator depends on the `ProcessorAdapter` protocol. `BatchProcessorAdapter` (`services/batch_adapter.py`) implements it over `processing/batch_processor.py`, which calls the `core/` wrappers. When PitStop is enabled, `_pitstop_adapter_factory` in `control_panel.py` supplies the adapter. Tests can inject fake adapters through this seam.

**Persistence.** `RunRepository` has in-memory (`services/repository.py`) and SQL (`services/sql_repository.py`) implementations. Production data is in SQLite (`image_magic.db`). The CLI records runs through `services/use_cases.py`, using the same run aggregate as the web app. While a run is active the coordinator keeps the aggregate in memory and persists one order per event (`save_order_with_event`); the whole-run `options_json` envelope is rewritten only at stage boundaries and at most every `IMAGE_MAGIC_ENVELOPE_CHECKPOINT_SECONDS` (default 5), so per-event cost must not grow with run size (`tests/test_run_persistence_scaling.py`). After a restart, unfinished runs are marked interrupted and finished history is kept.

**PDF folders.** A built PDF is routed by status (`services/pdf_routing.py`): `passed` → `PDF/Checked`, `warning` → `PDF/Rework`, `error` → `PDF/Failed`. `PDF/Print` is not a status folder: only the operator's «в печать» (`FileLifecycle.accept_for_print`) moves a PDF there, so nothing reaches Print before the decision; stale copies of the same name are still cleared from every folder, Print included; a stale copy that vanishes meanwhile (taken from Print; the CIFS mount uses `cache=loose`, so `is_file` can be stale) is skipped, not an error.

**Post-check actions.** `OrderWorkflowService` (`services/order_workflow.py`) handles accepting orders for print and returning them for rework, using `services/file_lifecycle.py` for file moves and `services/sborka_integration.py` for Sborka. A returned order goes to `Troubles/<order>/`: client sources at its top (next to the check-time copies and `.error.txt`), the built PDF in `PDF/`, previews in `Previews/` — the built PDF is named after the source (single PDF or face), so one flat folder would collide. Sborka kits (`services/order_kits.py`): `orderinfo` returns a kit only in the main order's record (`sets_array`; a sub-order alone returns `[]`), and returning the main order (`touser`) returns the whole kit in Sborka with one comment and the main's preview, while a sub-order return gets an empty reply. So with `kit_resolver` a return of any kit order sends only the main order to Sborka and returns every other kit order of the run locally (`kit_local`, no Sborka call), serialized per kit; a desynced kit (main already returned) is caught up locally, and printing a member of a returned kit is refused. Kits are stored as `order["kit"]` at check time, else resolved live once per run; when the main order is not in the run (already returned and moved), its number is guessed from the file name (`…(customer-order)_N` → order − (N − 1), `candidate_main_ids`) and accepted only if Sborka lists the order in that main's `sets_array`, a kit counts as already returned if its main is returned in this run or, within `KIT_RETURN_MEMORY` (3 days), in an earlier run or via a «returned with kit» action — then the rest is returned locally; if the main is not in the run and not yet returned, the return goes to Sborka under the main's number with the selected order's comment and preview (`kit_send_as`). An order still being processed by the active check (`RunCoordinator.order_in_progress`) is never moved — its result would overwrite the transition. The UI loads kits via `GET /api/checks/{id}/kits` (live `orderinfo`, cached per run and order) for the badge and the return-dialog warning. Layered TIFF print assembly is in `services/layered_tiff_print.py`.

**PitStop.** `services/pitstop/` runs report-only preflight over SSH and an SMB share, and is off by default. The order for each built PDF is PitStop, save reports, compute final status, then generate the production preview of that exact PDF revision. An order is not ready for print until PitStop finishes. Up to `IMAGE_MAGIC_PITSTOP_MAX_CONCURRENT` (default 4, `1` = strictly serial) checks run at once, measured on the live server on 2026-11-15; a transient failure is retried with no other PitStop check in flight, up to `IMAGE_MAGIC_PITSTOP_TRANSIENT_RETRIES` times (default 2) after a growing pause (`IMAGE_MAGIC_PITSTOP_RETRY_PAUSE_SECONDS`, default 3 s, then 6 s), and the PDF is fsynced to the SMB share before each attempt because PitStop Server sometimes cannot see a just-written file (error code 2018), and repeated transient failures switch the process to serial mode for a cool-down (`services/pitstop/concurrency.py`). Diagnose problem PDFs with `scripts/diagnose_pitstop.py`. A Callas fix (`services/callas_fix.py`) adds clipping and transparency of its own, so the PitStop check of an accepted-fix revision is compared with the check of the client's original PDF (`services/pitstop/baseline.py`, stored once as `order["pitstop_baseline"]`; for a side built from an accepted source fix it is the sum of PitStop checks of all the order's original source PDFs, run after the main check) by `action_id` and exact count (parsed from the message, since PitStop lists at most 100 locations). A fix that only drew bleed (`bleed_only` in the fix summary / `callas_source_fix`) is compared over every action (bleed strips bring low-res 1150, clipping, transparency and more; `IMAGE_MAGIC_PITSTOP_BLEED_FIX_ALL_ACTIONS`, default on; findings without `action_id` match by message with digits stripped); any other fix only for `IMAGE_MAGIC_PITSTOP_FIX_BASELINE_ACTIONS` (default `2079,3004`). Both only for `..._PROFILES` (default `digital`); the client's count keeps its severity, and what the fix added is hidden in the UI and does not count toward the verdict. For source fixes the baseline is each side's pre-fix PDF (`callas_source_fix["baseline_pdf"]`, also for raster sides) plus every unfixed PDF side, applied in both the production and the diagnostic-PDF branch of `BatchProcessorAdapter`; an order mixing bleed-only and other fixes uses the action list. A manual PDF replacement ends the comparison for that order. In `correction_policy == "auto"` runs the inspection itself tries the Callas `size_correction` plan on each file between the format and format + bleed (`services/callas_auto_bleed.py`, `BatchProcessor(auto_bleed=...)`, skipped when the PDF `reveal` applies), up to `IMAGE_MAGIC_CALLAS_AUTO_BLEED_MAX_CONCURRENT` (default 2) at once; a `bleed_only` result is accepted exactly like «Принять» (same `callas_source_fix`, so the baseline above applies) and marked `size_fix` `{"method": "bleed", "auto": true}`, anything else leaves the file to the normal size ladder, and a result for the same source signature is reused rather than re-run (`IMAGE_MAGIC_CALLAS_AUTO_BLEED_ENABLED`, default on; needs the Callas fix service).

**Check policies.** What PitStop findings may change an order's status depends on where its files lie (`config/check_policies.py` is the only data module, logic is in `services/check_policy.py`). `BatchProcessor.scan()` lists the input root and each folder of `IMAGE_MAGIC_STRICT_SOURCE_DIRS` (default `CorelDRAW`, created if missing, non-recursive, never one of `PDF/Previews/Troubles/Processed/output_report`; empty = none). Files in a strict folder get the `full` policy (every finding counts, as before); files in the root get `IMAGE_MAGIC_INPUT_CHECK_POLICY` (default `basic`; `full` switches the feature off and behaves exactly as before; an unknown value logs a warning and means `full`). An order with any strict-folder file, or started with the run option `check_policy: "full"`, is `full`; the choice is stored as `order["check_policy"]` (`{key, label, reason}`) and each file DTO has `source_folder` (`""` = root). Orders still group by (customer, order) across folders; a file with the same name in the root and a strict folder is an error for both (outputs, `Processed` and `Troubles` stay flat at the input root, so names would collide). In `basic` only these categories keep their severity: resolution, color model, ICC profile, page size/rotation, ink coverage, spot colors, fonts missing/incomplete, printable annotations, white overprint/knock-out; transparency, clipping, font types, invisible objects, thin lines and PDF actions are demoted to `information` (`policy_demoted`, `policy_original_severity`; `verdict_before_policy`/`counts_before_policy` keep the raw values) and no longer change the verdict, so the order can be green. A finding is matched to a category by `action_id` and, where one action means several things (2078: RGB / ICC / ICC for transparency group), by message regex; a finding matching no category keeps its severity and is flagged `policy_unclassified`, so a new PitStop check is never silently dropped. The policy runs after the fix baseline and before `completed_status` in every `BatchProcessorAdapter` branch and in `OrderWorkflowService.recheck_pdf_revision` (which reuses the stored policy); it never touches baseline-hidden findings, technical PitStop failures or the page-rule hard error. To add a check: one `CheckCategory` line in `CATEGORIES` plus one rule (`"status"`/`"info"`) per policy in `POLICIES`; to add a policy: a `POLICIES` entry. Policy fields that have no PitStop-table column are persisted in the run envelope (`__pitstop_policy__`), so no migration is needed.

**Rules.** Per-direction rules (`digital`, `offset`) are in `config/profiles.py`; add a direction as a new `PROFILES` entry rather than duplicating the engine. Accept/correct/confirm/reject decisions are made in `processing/resample_policy.py`.

## Processing invariants

- Never stretch width and height independently (sole exception: the bounded PDF `stretch` method below), and never use ImageMagick's forced `!` resize. Corrections scale proportionally to cover the target, then center-crop.
- Never convert color spaces automatically, with one exception: when `IMAGE_MAGIC_CALLAS_RGB_TO_CMYK_ENABLED` is on, a final PDF with RGB content is converted to CMYK by a callas pdfToolbox fixup (`IMAGE_MAGIC_CALLAS_RGB_TO_CMYK_PROFILE`, default `Image Magic/NEW_Convert color to 4c for digital printing`, which replaced the ISO Coated v2 profile; RGB presence is decided by `find_rgb_pages` before/after, and ICC/Lab color found beforehand is reported as `icc_removed` / the "ICC off" badge), and the result replaces the PDF only if no RGB remains and the page count is unchanged. On any failure the RGB PDF is kept with a warning. A PDF with no RGB but with an ICC-CMYK/Gray profile or an OutputIntent (PitStop 2078) is run through the same callas profile to strip them without recalculating values (`find_icc_pages`, `color_conversion.reason == "icc"`, verified locally, `IMAGE_MAGIC_CALLAS_STRIP_ICC_ENABLED`, default on); if Lab is present it is left untouched (`status: skipped`, `skip_reason: lab`), and on failure or when ICC remains the PDF is kept with a warning. Source images are never recolored; other color models (Gray, Lab, spot) are left alone.
- PDF page sizes are corrected only when `IMAGE_MAGIC_CALLAS_PDF_RESIZE_ENABLED` is on (`processing/pdf_resize_policy.py`). Per page the softest decision wins, and at equal decision the ladder order `reveal` < `stretch` < `shrink` < `fill`: `reveal` (page smaller than the format and a background object already extends past the edge, per `PdfPageInfo.hidden_margins_mm` → `enlarge_pages`, no scaling), `stretch` (`stretch_to_fill`), `shrink` (proportional downscale) or `fill` (enlarge or crop only); `shrink` and `fill` use the same `analyze_resample` rules as rasters → `scale_pages fit_from_outside_cut_page`. Stretch is the only allowed exception to "never stretch independently": PDF only, only within the profile's `pdf_stretch_auto_pct` / `pdf_stretch_confirm_pct` (default 1% / 3%), and a candidate with ~0 distortion (< 0.01%) counts as shrink/fill. Reveal growth and shrink/fill crop share the `auto_crop_mm` / `confirm_crop_mm` limits. A downscale (raster or PDF, including a stretch that shrinks both sides) is automatic only if the artwork exceeds the format by at most `shrink_auto_mm` (default 2 mm) on its larger side, or if the source is below `min_dpi` and the shrink brings it up to `min_dpi` (vector pages: size rule only); otherwise it needs confirmation. In run mode «Автоматически принимать малые коррекции» the full ladder is reveal → Callas bleed → stretch → shrink → fill, and each applied correction is a `FileCheck.size_fix` mark (`method`, `auto`, `from_mm`, `to_mm`, `detail`) instead of a warning line. A file whose name contains a no-scale marker (`PrePressProfile.no_scale_name_markers`, default `(SRA3P)`, `(SRA3)`, `(BAN)`, case-insensitive, parentheses included; `IMAGE_MAGIC_NO_SCALE_NAME_MARKERS`, empty = off) skips the whole ladder and Callas auto bleed: its size is fixed only by `canvas` (`analyze_canvas`, same `auto_crop_mm` / `confirm_crop_mm` limits, no rotation) — white margins or a centered crop with no scaling, rasters via `canvas_image` at source DPI, PDFs by moving the MediaBox (`set_page_box`, signed per-side offsets in `PdfPagePlan.enlarge_mm`). The expected file size is normally the name's format + 2 × bleed, but `PrePressProfile.reference_sizes_mm` overrides it by marker: `(SRA3)` = 314×434 and `(SRA3P)` = 324×471 mm, already including bleed, either orientation, whatever size the name declares (`expected_size_mm`, used by inspection, manual PDF revision checks and the audit DB; exposed as `FileCheck.expected_mm` / DTO `expected_mm` for the UI). Afterwards CropBox = BleedBox = MediaBox and TrimBox is inset by the bleed. The JSON goes through the wrapper profile `Image Magic/Apply QuickFix config` (built by `scripts/build_quickfix_profile.py`) in the `quickfix_config` variable (max 1024 chars; a two-page worst case is ~920). A bad QuickFix silently changes nothing, so `services/callas/page_resize.py` accepts the result only after checking page count, MediaBox, TrimBox and BleedBox. Pages with `/Rotate` are not resized.
- A PDF has 1 or 2 pages (`MAX_SUPPORTED_PAGES`), and a 2-page PDF is a complete duplex order. The pages of all the order's files together may not exceed its printed sides (2 for duplex, 1 for one-sided; a raster counts as 1 page, `_validate_page_total`). Breaking this (a PDF over 2 pages, a 2-page PDF for one-sided printing, a 2-page PDF next to other side files, several 2-page PDFs, three side files…) sets `page_rule_violation` and is a hard error (`has_page_rule_violation`): the order stays `error` even with a diagnostic PDF and any PitStop verdict, so it cannot be printed. Other local findings with a diagnostic PDF still end as `warning`. For a 2-page PDF next to other side files (order 26237111) the diagnostic PDF is built from the 2-page PDF alone (`_diagnostic_files`), not glued into 3 pages; the order is still red and goes back for rework.
- `50×90` and `90×50` are equally valid: name order does not define the top of the artwork, and one-sided orders are not auto-rotated. The final-PDF size check (`_validate_created_pdf`) therefore accepts either orientation, and it measures the final PDF's page boxes (`inspect_pdf`, the same way the source was measured), not the 72-DPI callas control render: the render rounds down and loses up to 1 px more (49×74 mm came out as 48.7×73.4, order 26242148) and applies `/Rotate`; the render pixels are only a fallback (tolerance 0.75 mm).
- All PDF operations (merge, page split, info, render) go through callas pdfToolbox, with no PyMuPDF/Ghostscript fallback; raster TIFF/JPEG/PNG → PDF conversion stays on ImageMagick. A final PDF is published only after a callas pdfToolbox control render; PDF rendering never falls back to Ghostscript or PyMuPDF, and fails with an actionable error when callas is not configured.
- Reviewed layered TIFF exports do not replace the production PDF. A print assembly built from them gets its own PitStop result, shown separately from the original PDF's report.

## Configuration

Settings come from `IMAGE_MAGIC_*` environment variables, read by `Settings.from_env()` in `server/settings.py`. User paths are confined to `IMAGE_MAGIC_ALLOWED_ROOTS`. Logs are written to `logs/image-magic.log`.

Temporary work folders on the SMB share (`/mnt/shared`) must use `core/share_tempdir.share_temp_dir`, not `tempfile.TemporaryDirectory`: on CIFS a file still held open by another client (callas, PitStop) makes `rmdir` fail with `[Errno 39] Directory not empty` for a moment, so cleanup is retried (0.5/1/2 s) and then only logged (`share_tempdir.cleanup_deferred`), never failing an order whose PDF is already published; `create_pdfs` and the diagnostic PDF sweep hidden Image Magic temp folders older than an hour (`sweep_stale_temp_dirs`).
