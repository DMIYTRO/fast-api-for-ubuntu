# Тестовая сборка callas pdfToolbox: Checks and Fixups

[Полный справочник команд CLI 17](COMMANDS.md) — действия, диагностика,
лицензирование и ссылки на официальное руководство callas.

Отдельная инструкция для проверки типовых проблем печати на **копиях** заказов.
Профили собираются и проверяются в настольной версии pdfToolbox, затем
экспортируются в `.kfpx` и выполняются через pdfToolbox CLI на Linux.
Это тестовый контур, не интеграция с рабочим FastAPI-сервисом.

  `README.md` и тест разделения/объединения PDF. В новом репозитории

  вылеты, красочное покрытие, тонкие линии, плашечные цвета, прозрачность,
  визуальное сравнение и хранение ревизий. Это **проектные идеи**, а не
  подтверждение, что все пункты реализованы в CLI.
- `core/callas_toolbox.py` показывает текущие вызовы проекта: объединение PDF,
  перевод поддерживаемых растров в PDF и создание preview. Тестовые скрипты
  находятся в `scripts/` основного проекта.

Подробное назначение **каждой доступной команды CLI 17** вынесено в
[COMMANDS.md](COMMANDS.md). Старого единого списка команд в истории проекта
не обнаружено; справочник составлен по встроенной помощи установленной
версии и официальному руководству Callas.

## Что проверяем

| Задача | Check (обнаружение) | Fixup (исправление копии) |
| --- | --- | --- |
| Недостаточные вылеты | Объекты у TrimBox, пустая или недостаточная зона BleedBox | Generate bleed at page edges; способ и ширина задаются в профиле |
| Неполноцветный чёрный | Цвет векторных/растровых объектов, RGB/CMYK, значения каналов | Раздельные Fixup для вектора и растра после согласования целевого чёрного |
| Тонкие линии плашечного цвета | Толщина линии, имя Spot Color, overprint | Изменение толщины/overprint только после проверки, что линия не техническая |
| Прозрачность и маски | PDF transparency, soft mask, blend mode | Flatten transparency только при необходимости и после визуального сравнения |

Каждую проблему оформляем отдельным профилем с понятным именем и версией.
Сначала запускаем **Check без изменений**, затем — Fixup на отдельной копии.
Не включаем все исправления в один профиль, пока каждый из них не прошёл
проверку на реальных примерах и отрицательных контрольных файлах.

## 1. Установка тестового контура

1. Установить официальную настольную версию pdfToolbox на рабочем месте, где
   создаются профили. Для CLI скачать **отдельный пакет для нужной ОС и
   архитектуры** с сайта callas software. Не переносить бинарник macOS на Linux.
2. Распаковать CLI в каталог вне этого репозитория и убедиться, что команда
   `pdfToolbox -h` работает. Версию зафиксировать в журнале теста.
3. Активировать лицензию **для pdfToolbox CLI и этой платформы** согласно
   инструкции callas. Лицензию, файл активации и кэш не коммитить. Проверить
   `pdfToolbox --cachefolder=/путь/к/cache --status`: нужный продукт должен
   иметь действующий срок. На дату составления инструкции прежняя тестовая
   лицензия истекала 16.09.2026; её текущую пригодность всегда проверять заново.
4. Подготовить три отдельные папки вне репозитория: `input/` (копии заказов),
   `output/` (результаты), `cache/` (локальный кэш лицензии). Исходные файлы
   открыть только на чтение; результат всегда писать по новому пути.
5. Проверить свободное место и права записи в `output/`. Для сетевой папки
   предварительно сделать короткий пробный запуск на одном файле.

В уже настроенной тестовой VM `10.20.2.104` бинарник расположен в
`/home/ubuntu/v2-web-platform-FastApi/tools/callas_pdfToolboxCLI_x64_Linux_17-0-682/pdfToolbox`.
Это **пример существующей установки**, а не требование к новому серверу.
Производственный сервис `fastapi-app` ради этих тестов не перезапускается.

## 2. Создание профиля в Desktop

1. Открыть несколько проблемных и контрольных PDF в pdfToolbox Desktop.
2. В разделе **Checks and Fixups** создать Check для конкретной проблемы.
   Указать точный порог и область применения: например, ширину вылета,
   толщину линии, конкретные Spot Color. Сохранить название и описание.
3. Запустить Check. Сверить найденные объекты с PDF визуально: нужны как
   ожидаемые попадания, так и примеры, которые Check не должен отмечать.
4. Создать отдельный Fixup. Для вылетов выбрать метод продолжения изображения
   (отражение объектов/краёв, повторение пикселей и т. п.) и необходимую
   ширину. Для цвета зафиксировать требуемую модель и конкретные значения;
   для линий — минимальную толщину и исключения для технических цветов.
5. Запустить Fixup **только на копии**, сравнить до/после, геометрию страниц,
   Spot Color, overprint, прозрачности и качество растра. Проверить хотя бы
   один PDF, где изменение не требуется.
6. Экспортировать профиль в `.kfpx`, записать версию и дату. Список готовых
   профилей вести отдельно; в репозиторий добавлять только профили,
   разрешённые к распространению.

Название `Checks and Fixups` относится к редактору проверок и исправлений.
**Check не изменяет PDF; Fixup меняет выходную копию.**

## 3. Запуск через CLI

Ниже `CLI`, `CACHE`, `PROFILE`, `INPUT` и `OUTPUT` — примеры переменных пути.
Подставить реальные абсолютные пути. Для теста брать PDF, не исходный CDR/PSD.

```bash
CLI=/путь/к/pdfToolbox
CACHE=/путь/к/cache
PROFILE=/путь/к/profile.kfpx
INPUT=/путь/к/input/example.pdf
OUTPUT=/путь/к/output/example.checked.pdf

"$CLI" --cachefolder="$CACHE" --status
"$CLI" --cachefolder="$CACHE" --noprogress \
  --outputfile="$OUTPUT" "$PROFILE" "$INPUT"
```

Для **профиля только с Check** дополнительно сохранить стандартный отчёт
Callas в отдельный каталог:

```bash
"$CLI" --cachefolder="$CACHE" --noprogress \
  --report=JSON,ALWAYS,PATH=/путь/к/output/example.report.json \
  "$PROFILE" "$INPUT"
```

Для **Fixup** всегда указывать новый путь `--outputfile`, отличный от
входного. Если Fixup пишет выходной PDF и отчёт, сначала проверить эту
комбинацию на одном файле: некоторые варианты профиля/сетевой файловой системы
не сохраняют оба результата при одном запуске. В таком случае выполнять
Check и Fixup отдельными вызовами и сохранять текстовый вывод CLI.
Не считать любой ненулевой код ошибкой: для профилей коды 1–8 могут означать
найденные проблемы или выполненные исправления; коды 100+ — ошибки выполнения.
Всегда дополнительно проверять существование и размер выходного файла.

## 4. Протокол теста и критерии приёмки

Для каждого файла фиксировать: исходное имя, размер до/после, время обработки,
название и версию профиля, код завершения, число и тип находок, число Fixup,
путь к результату и результат визуального сравнения. Отдельно измерять
общее время серии. Сначала запускать последовательно; параллелизм повышать
после проверки лимита лицензии, RAM и сетевого диска.

Профиль допускается в поток только если он не меняет исходник, исправляет
заданные примеры, не затрагивает контрольные файлы и оператор подтвердил
качество PDF до/после. При ошибке не подменять исходный или уже готовый PDF;
оставить лог и отправить файл на ручную проверку.

## Ограничения

- Callas проверяет содержимое PDF. Он не доказывает, были ли сведены слои
  исходного TIFF, PSD или CDR до экспорта.
- Конвертация TIFF в PDF показывает только то, что сохранилось в PDF.
  Soft mask после конвертации не равна доказательству именованного
  альфа-канала в исходном TIFF.
- CDR не является штатным входным форматом этого теста; PSD нельзя считать
  надёжным источником для автоматической проверки структуры слоёв.
  Экспортировать их в PDF в соответствующем приложении, затем проверять PDF.
- Поля Creator/Producer могут указывать приложение-создатель документа, но
  не происхождение отдельной маски или объекта.
- «Дорисованный» вылет может выглядеть неверно на тексте, логотипе или
  сложной композиции: визуальная проверка обязательна.
